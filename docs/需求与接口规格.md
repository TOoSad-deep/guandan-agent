## 2. 使用场景与术语

### 2.1 主要使用场景

1. 开发者配置平台及策略版本，启动参赛程序并查看运行状态。
2. 系统根据平台请求自主出牌，必要时进行一次战术复核。
3. 演示者查看牌局、决策理由、复核修改和异常兜底过程。
4. 实验人员运行不同策略版本，查阅日志、复盘和统计结果。

### 2.2 统一术语

| 术语 | 本文含义 |
| --- | --- |
| 小局 | 一次发牌后，按照平台规则产生结算的游戏过程 |
| 整场 | 当前已验证快照中的一次完整升级赛，包含多个小局；教师版本仍待确认 |
| 一次决策 | 针对一个有效动作请求，从准备输入到确定处理结果的过程 |
| 可见局势 | 本人手牌与平台允许该玩家获得的公开信息 |
| 合法动作集合 | 平台针对当前请求提供的完整可选动作集合 |
| 候选集合 | 从合法动作集合筛选后提供给模型的动作集合，保留与原动作的对应关系 |
| 局势快照 | 一次决策所依据的可见局势、请求和候选版本，不随迟到响应改变含义 |
| 复核 | 对同一次决策的补充检查或输出修复，最多发生一次 |
| 规则兜底 | 在有效请求下，通过确定性规则选择合法动作，不再调用模型 |
| 已发送 | 已将动作交给通信过程，不证明平台接受 |
| 已确认 | 已取得按平台协议能够证明该动作被接受的反馈 |
| 过期请求 | 被新有效请求替代、阶段已结束、超过平台期限，或经平台确认已失效的请求 |

### 2.3 三个评测版本

| 版本 | 决策方式 | 每次决策的在线模型请求上限 |
| --- | --- | ---: |
| V0 | 确定性规则策略 | 0 |
| V1 | 规则工具辅助主 Agent，不启用复核或模型修复 | 1 |
| V2 | 与 V1 相同的基础流程，按条件增加一次复核或修复 | 2 |

V2 的普通局面最多调用一次。唯一合法动作可以直接执行，模型请求数为零。三个版本使用相同的平台接入、状态维护、最终合法性检查及日志口径；V1 和 V2 的候选生成、主模型配置与兜底策略保持一致。

## 3. 全局行为约束

| 编号 | 约束 | 可观察要求 |
| --- | --- | --- |
| C01 可见信息 | 在线模型和规则策略只使用当前玩家允许获知的信息；不得读取队友或对手的实际隐藏手牌 | 保持可见信息不变、仅改变测试环境隐藏手牌时，准备给策略的局势和工具特征不变 |
| C02 事实与判断分开 | 平台事实由程序维护，模型猜测不得覆盖事实；未知数量不得默认为零 | 对手过牌后不把“没有更大牌”写成事实；模型猜牌只显示为推测 |
| C03 动作来源 | 提交动作必须来自当前请求的合法集合；模型不能自行拼接牌组 | 能从每个提交动作追溯到其原始合法选项 |
| C04 同一次请求绑定 | 候选编号仅在其所属请求和快照内有效；执行前再次检查有效性 | 旧编号不得按新候选列表解释；旧请求的模型结果及规则备选均不得提交 |
| C05 调用总量 | 实际发起的在线模型请求按同一次决策累计，失败请求和重试也计数；切换角色不得重置预算 | V1 无第二次请求，V2 无第三次请求；同时命中多个风险也最多复核一次 |
| C06 时间预算 | 工具计算、模型等待、复核、校验均受决策总预算约束，并为提交保留余量 | 模型等待超时后仍有机会执行规则备选；平台期限已过则放弃旧决策 |
| C07 执行证据 | 发送、接受、拒绝、未确认分别记录；不根据网络发送成功推断已执行 | 提交后未获接受证据时，界面和日志不得显示已确认 |
| C08 隔离与归属 | 不同比赛、座位和请求的状态、推测及结果不得串用 | 新小局替换旧手牌，保留必要比赛级信息；另一座位的私牌不进入本玩家输入 |
| C09 记录与凭证 | 关键结果可关联到具体决策；API 密钥等凭证不写入模型输入、普通日志或提交源码 | 演示和导出的记录不含密钥；缺失记录明确标注，不伪造过程 |

平台正式期限仍待确认；阶段五的本地初始预算、候选与输出限制见第 12.3 节，不能视为模型满足正式时限的保证。

## 4. 核心功能需求

### F01 比赛平台接入

**触发场景：** 启动或停止参赛；收到平台通知、动作请求、结算或连接异常。

**输入：** 指定平台配置、参赛身份或座位、所选策略版本及平台消息。仅使用当前玩家获准接收的信息，不从服务端内部读取其他玩家私牌。

**预期行为：** 按指定协议创建或加入比赛，识别出牌、进贡、还贡和结算阶段；将有效请求交给策略处理，并按该请求提交合法动作。非本人动作请求不得触发本玩家出牌。停止参赛后不再发起新决策，未完成比赛按实际平台结果记录。

**输出与结果：** 可区分连接、入局、等待动作、决策中、结束及中断状态；消息可归属到对应比赛和玩家。小局结束与整场结束分别记录，结算以平台证据为准。

**异常情况：** 无法连接或入局时显示原因，不标为正在比赛；未知消息不擅自解释为出牌请求。缺少合法动作或无法确认当前阶段时，不提交猜测动作。断线或提交结果不明时暂停提交，核对平台状态；平台不能恢复原局时标记中断，不自动把新比赛当成原局继续。

**验收条件：**

| 案例 | 给定条件或操作 | 预期可观察结果 |
| --- | --- | --- |
| AC01-01 | 使用规则版本连接指定平台，依次经历等待、本人出牌及结算 | 仅响应本人有效请求；取得结算并关联完整对局记录 |
| AC01-02 | 分别提供进贡、还贡及不需要贡还牌的场景 | 使用对应阶段的合法选项，保留协议要求的关联信息；未发生阶段不强行执行 |
| AC01-03 | 动作提交后断开连接，无法确认接受或恢复 | 显示未确认或中断，不重复出牌，不伪造胜负 |

### F02 对局状态与记牌

**触发场景：** 初始化小局；收到已确认的出牌、贡还牌、级牌变化、玩家出完或结算信息。

**输入：** 本人手牌、平台公开的历史与剩余张数、座位关系、当前领先动作和阶段信息。平台未公开的数据保持未知；模型意见单独保存。

**预期行为：** 按实际牌数更新记录，区分两副牌中重复的牌面；同步处理进贡和还贡。当前事实、公开历史、模型推测和执行进度分开维护。明确的重复通知只应用一次；不同决策里恰好相同的牌面不能当成同一事件去重。进入新小局时清理过时手牌和推测。

**输出与结果：** 提供与平台已知事实一致的可见局势快照；对计数不一致、缺失历史和未知信息给出明确状态。仅发送动作不提前将其确认为已经出牌。

**异常情况：** 出现负数计数、无法解释的张数冲突或消息顺序不明时，不静默修补事实；优先获取平台权威状态。不能恢复可信状态时停止基于该状态的模型推理；只有当前请求自身足以确定有效合法动作时才允许规则处理，否则暂停该局动作提交。

**验收条件：**

| 案例 | 给定条件或操作 | 预期可观察结果 |
| --- | --- | --- |
| AC02-01 | 本人有两张相同牌面，确认打出一张；随后完成一次贡还牌交换 | 相同牌面剩一张，交换后的牌数及已知归属正确，无重复扣减 |
| AC02-02 | 重放一条可确认重复的通知；另在后续真实决策中打出相同牌面 | 重复通知不重复扣牌；后续独立出牌正常扣牌 |
| AC02-03 | 改变对手私牌但保持可见信息一致；模型再猜测对手无对子 | 策略可见快照及特征不受隐藏牌变化影响，猜测不修改事实 |

### F03 手牌分析与候选筛选

**触发场景：** 有效请求具备可信的可见局势和非空合法动作集合，需要准备模型输入或规则备选。

**输入：** 本人手牌、合法动作及当前公开局势。不得利用其他玩家真实手牌来计算威胁或团队牌力。

**预期行为：** 为动作提供出牌数量、剩余张数、剩余组合估计、散牌和拆牌代价等简单特征；按确定的规则排序并筛选候选。特征应基于出牌后的剩余手牌，而不只评价打出的牌。

初版候选保留要求如下：存在合法过牌时保留；存在可直接出完本人手牌的动作时保留；当前领先者为临近走完的对手且有合法压制动作时，至少保留一个压制选项。平台不允许过牌时不得自行加入。必要选项数量超过普通筛选目标时，优先保留必要选项并记录原因；模型输入限制无法容纳时转规则处理，不静默遗漏。

**输出与结果：** 非空候选、每项对应的原始合法动作、特征摘要和规则备选。组合数量注明是估计，不宣称等于实际走完回合数或最优胜率。只剩一个合法动作时可跳过模型。

**异常情况：** 特征计算失败或超过工具预算时停止复杂分析，记录降级原因并使用当前完整合法集合中的确定性规则选项。平台合法集合为空或不可用时，不调用模型编造动作，按 F01/F06 处理。

**验收条件：**

| 案例 | 给定条件或操作 | 预期可观察结果 |
| --- | --- | --- |
| AC03-01 | 合法集合包含过牌、直接走完和满足保留条件的压制选项，执行候选压缩 | 必要选项仍在，每项均对应原始合法动作；首出不允许过牌时不新增过牌 |
| AC03-02 | 剩余手牌含某个当前不能压住上家、但可在后续首出的组合 | 该组合仍可纳入手牌结构分析，不因当前跟牌列表缺少它就判不存在 |
| AC03-03 | 当前只有一个合法动作 | 零次模型调用，完成校验后提交该动作，记录直接执行原因 |
| AC03-04 | 模拟分析失败或筛选异常为空，但完整合法集合仍有效 | 使用完整集合中的规则备选；若完整集合也为空则无动作提交 |

### F04 主决策 Agent

**触发场景：** V1/V2 收到需要模型判断的有效请求，已准备好可见快照和候选，且仍有时间与调用预算。

**输入：** 本人手牌与公开局势摘要、候选及特征、当前阶段规则提示。历史裁剪不得改变关键事实；历史不完整时明示缺失。

**预期行为：** 在候选中选择一个动作，综合考虑自身走牌、协助队友和对手威胁；输出可解析的动作选择、简短理由及必要风险提示。动作选择应有明确的候选编号对应关系，具体编号与输出格式见第 8.3、11 节。

**输出与结果：** 一个待校验建议，以及模型调用耗时和可获得的用量信息。模型生成的理由和风险提示不视为已证实事实或策略最优的证明。

**异常情况：** 无效编号、多个互相冲突的选择、不可解析或缺失必要内容，均视为无效建议，不直接提交。V1 进入规则兜底；V2 在请求有效且仍有预算时可进行一次修复或复核。服务调用失败或等待超时则转规则处理，不无限请求模型。迟到输出按 F06 弃用。

**验收条件：**

| 案例 | 给定条件或操作 | 预期可观察结果 |
| --- | --- | --- |
| AC04-01 | 普通局面模型返回有效候选选择和理由 | 一次调用，保留理由，选择进入程序校验；不能直接绕过校验提交 |
| AC04-02 | 模型返回越界编号、空输出或自行拼出的牌组 | 不提交该建议；V1 规则处理，V2 仅在预算内允许一次修复 |
| AC04-03 | 模型服务失败或超过等待预算，当前请求仍有效 | 记录失败和实际尝试次数，使用合法规则备选，无无限重试 |

### F05 条件触发的战术复核

**触发场景：** V2 的主建议触发风险条件，或其输出需要修复；当前请求仍有效，且尚未复核、未耗尽两次调用及总时间预算。

**输入：** 与主决策相同的可见局势及候选快照、主建议或失败原因、具体触发条件。有效主建议可附理由，但不得把模型理由提升为事实。

**预期行为：** 对对手只剩一两张、使用炸弹、压过领先队友、触发已定义拆牌代价条件等情况进行检查。拆牌代价阈值待工具验证后确定，未定义的触发器不宣称已启用。多个条件合并为一次复核。复核可维持原动作或改选同一候选集合中的动作；输出修复和战术复核共用这一次机会。

**输出与结果：** 最终建议动作、维持或修改标记、简短依据及实际触发原因。动作仍需接受最终程序校验；模型“没有风险”不能跳过校验。

**异常情况：** 复核输出无效、服务失败或超时后不再修复，转规则备选。仅因时间不足而没有启动复核时，若主建议有效则校验后执行主建议，并记录跳过原因；主建议无效则规则处理。请求已过期时两者均不得提交。

**验收条件：**

| 案例 | 给定条件或操作 | 预期可观察结果 |
| --- | --- | --- |
| AC05-01 | 主建议同时触发对手剩一张和使用炸弹 | 仅复核一次，日志包含两个触发原因；总调用不超过两次 |
| AC05-02 | 复核维持原动作；另一个案例改选有效候选 | 分别记录维持和修改，使用相同快照，修改动作经最终校验后提交 |
| AC05-03 | 主输出无效，第二次修复仍无效 | 直接进入规则备选，不产生第三次模型请求 |
| AC05-04 | 风险触发时预算不足以启动复核 | 不调用复核；有效主建议经校验使用，无效主建议规则处理，日志说明跳过原因 |

### F06 动作校验与异常兜底

**触发场景：** 主决策、复核或规则策略给出动作；模型或工具失败；请求发生变化；动作发送后收到反馈或连接中断。

**输入：** 当前请求及其合法动作、待选建议、局势与候选的对应关系、已用预算、连接和提交状态。不将模型给出的“合法”结论作为校验依据。

**预期行为：** 提交前确认编号对应正确快照、动作属于当前合法集合、阶段和请求仍有效、存在提交时间且连接可用。模型失败时使用原先准备的规则备选，但同样重新校验。一次请求只能形成一个有效提交决定；备用已发送后，迟到模型结果不得触发第二次提交。

**输出与结果：** 明确区分待提交、已发送、已确认、被拒绝、结果未确认和请求已作废，并附原因。本人手牌等事实由平台确认信息更新。若协议以状态广播确认动作，必须先在阶段三验证其可对应关系。

**异常情况：** 没有可信合法集合、请求失效、期限已过或连接不可用时，不承诺一定能出牌，应停止该次提交并记录原因。状态不明时不盲目重发。只有明确被拒绝、平台仍允许当前请求重提且有足够时间时，才可按已验证协议提交一个合法规则动作；不能识别重复与拒绝语义前，不启用自动重提。

**验收条件：**

| 案例 | 给定条件或操作 | 预期可观察结果 |
| --- | --- | --- |
| AC06-01 | 模型选择映射为当前合法动作，平台随后确认接受 | 对应完整动作提交一次；接受证据到达前仅标记已发送，到达后标记已确认 |
| AC06-02 | 旧候选编号在新请求中恰好对应另一个动作，旧结果迟到 | 丢弃旧结果，不按新列表解释；旧备选也不能提交 |
| AC06-03 | 模型等待超时，规则备选提交后模型又返回不同动作 | 规则备选仅提交一次，迟到结果仅记录，不覆盖决定、不再次发送 |
| AC06-04 | 平台拒绝动作，或发送后一直没有明确反馈 | 拒绝与未确认分别显示，不标记已执行；未确认不盲目重发 |
| AC06-05 | 已到平台期限、连接已断开或合法集合为空 | 无猜测动作发送，记录本次未能执行；是否判负以平台结果为准 |

### F07 基础界面与决策记录

**触发场景：** 对局开始或更新、模型决策、复核、提交和结算发生；用户浏览当前或历史决策。

**输入：** 可见牌局、各步骤结果、提交反馈、耗时、用量和错误原因。模型凭证不得进入展示数据；可见局势与赛后获知信息应有区别。

**预期行为：** 展示当前牌局与等待、分析、复核、兜底、提交等状态；按决策查看局势摘要、候选、所选动作、简短理由、复核修改和平台结果。记录决策来源，区分规则选择、唯一动作直出和模型选择。模型和通信等待期间仍可浏览已有日志。

**输出与结果：** 能对应具体比赛、小局和决策的可浏览记录；未知耗时、未返回用量或缺失结果不能显示为零或成功。基本日志从规则对局开始就产生，不等到复盘阶段补造。

**异常情况：** 理由缺失、日志缺项和写入失败均应明确提示。界面故障不重复触发动作；日志或展示失败不应占用剩余出牌时间进行无限修复。无法留存完整证据的运行标为记录不完整，评测与复盘不得据此声称完整验证。

**验收条件：**

| 案例 | 给定条件或操作 | 预期可观察结果 |
| --- | --- | --- |
| AC07-01 | 各运行一次普通决策、复核修改和规则兜底 | 页面及日志均能找到对应输入、动作、来源、原因和平台结果 |
| AC07-02 | 模型持续等待，用户浏览上一回合 | 已有记录可浏览，当前显示等待而非完成，不因浏览重复决策 |
| AC07-03 | 用量缺失、写日志失败或连接未确认 | 明示未知或记录不完整；不显示零费用或已确认，凭证不出现在日志中 |

### F08 赛后复盘

**触发场景：** 收到对局结束信息后自动或由用户发起复盘；对中断记录可以生成明确标为不完整的分析。

**输入：** 已保存的局势、候选、动作、复核意见、后续公开事件和实际结算。应区分当时可知的信息与事后结果，不将后来得知的隐藏牌补入当时的决策输入。

**预期行为：** 选择有记录支持的关键决策，说明当时选项、实际行为、后续结果和待验证建议。每项结论引用对应决策；没有对照模拟时，不断言另一个动作必然获胜，也不把单次输赢完全归因于某个动作。

**输出与结果：** 可点击或定位到回合记录的复盘内容，区分事实、解释与建议。复盘调用作为离线用量单独记录，不计入在线两次调用预算；下一局开始时不得等待上一局复盘完成。

**异常情况：** 缺失日志、模型失败或超时则保留原始记录，标记复盘未完成或依据不足；不伪造遗漏回合。复盘结果不自动修改规则权重、在线提示词或已冻结的评测配置。

**验收条件：**

| 案例 | 给定条件或操作 | 预期可观察结果 |
| --- | --- | --- |
| AC08-01 | 对完整对局复盘，模型选出若干关键决策 | 每项可定位真实记录，描述与动作及后续结果一致 |
| AC08-02 | 日志缺少关键回合，或结算后才披露其他玩家牌面 | 明确缺失和事后信息，不编造当时依据，不生成必胜保证 |
| AC08-03 | 复盘模型失败，同时下一局已开始 | 保留对局日志并标复盘失败，下一局正常进入决策，在线配置未被改变 |

### F09 对战评测与统计

**触发场景：** 启动指定策略版本的实验，收到结算或异常结束，生成对比报告。

**输入：** 策略版本、平台和规则版本、对手与队友配置、座位、实际初始局面或可用随机条件、时间预算、运行环境、平台结果和决策日志。模型及提示配置变化应可识别；缺失条件标记未知。

**预期行为：** 分别统计 V0/V1/V2 的小局成绩和整场成绩、耗时、实际模型请求次数、Token、可核算费用、超时、兜底和复核修改次数。明确启动数、已结算数、中断数、未确认数以及胜率分母；平台有明确判负时按其结果统计，同时保留异常原因。

固定发牌能力未验证前不声称严格配对。支持时核对实际初始牌局及配对关系，轮换座位后按同源牌局或整场组织统计。测试前冻结配置；调参用的数据与最终评测数据分开，不用复盘自动改动测试中的策略。

**输出与结果：** 可关联到各场比赛和决策记录的对比表，报告表现和成本，允许结论为“未观察到改善”。三版本比较主要检验引入模型和增加复核的作用，不宣称已单独证明每个工具的收益。

**异常情况：** 无结算或关键日志缺失时不补造胜负、用量或费用；列出缺失样本和可统计范围。收费信息不可核实时费用显示未知或明确标记估算依据。不同对手、规则或时间预算的结果分开列出，不直接混成一个提升数字。

**验收条件：**

| 案例 | 给定条件或操作 | 预期可观察结果 |
| --- | --- | --- |
| AC09-01 | 用相同候选规则、主模型、兜底及对战条件运行 V1/V2 | 报告区分有无复核，同时展示成绩、耗时、调用量和复核修改量 |
| AC09-02 | 启动 10 场，其中 8 场有完整结算、1 场中断、1 场结果未确认 | 三类数量均列出，胜率分母清楚；后两场不擅自判胜负；明确平台判负另按结果处理 |
| AC09-03 | 同一发牌轮换多个座位，且部分调用无费用数据 | 保留共同发牌归属，不当作独立发牌样本；费用未知不记为零 |

## 5. 跨功能分支规则

各功能发生冲突时，先检查请求是否有效，再考虑模型建议和预算。复核只能改变建议，不能恢复过期请求或突破合法性约束。

| 当前情况 | 应执行的行为 | 关键记录 |
| --- | --- | --- |
| 唯一合法动作且请求有效 | 直接校验并执行，不调用模型 | 直接执行、动作来源 |
| 主建议有效，未触发复核 | 最终校验后提交 | 主选择、平台反馈 |
| V2 命中多个风险且预算充足 | 合并触发一次复核 | 全部触发原因、是否改选 |
| V2 主输出无效且尚有第二次机会 | 在同一候选快照内进行一次修复 | 原失败原因、第二次结果 |
| 主建议有效但复核预算不足 | 跳过复核，校验主建议后执行 | 跳过原因；不记作已复核 |
| 主建议无效且不允许再调用 | 使用当前有效请求下的规则备选 | 兜底原因 |
| 已启动的复核失败或超时 | 不再请求模型，转规则备选 | 第二次失败、实际调用数 |
| 请求过期或比赛结束 | 丢弃待处理及迟到决策，不提交旧备选 | 作废原因 |
| 规则备选已经发送，模型才返回 | 保留迟到记录，不改决定、不再发送 | 迟到输出和已发送状态 |
| 动作已发送但平台结果不明 | 核对状态；核对前不盲目重发 | 未确认及连接状态 |

## 8. 技术约定与数据结构（阶段五）

以下为 v1.10 接口基线。B01—B09 已实现在线闭环、HTTP、离线复盘与统计，具体范围见[实施计划第 7 节](实施计划.md)；P20真实报告生成/浏览流程通过，文本事实准确性未通过抽查，结构与引用校验不能代替内容质量判断。V2 的真实模型验证采用合成输入，尚无自然实局复核确认，不代表完整模型比赛或策略效果。第 1—7 节仍是行为与验收依据；接口有冲突时先修正文档再改实现。公共字段集中维护在 `src/guandan_agent/contracts.py`，不为每个结构单独建立包。

### 8.1 公共约定与编号

- 结构使用严格类型校验，拒绝未知字段和类型强制转换；列表发布前深复制/冻结，调用方不能修改 Session 持有的对象。以下 `T?` 表示可为 `null`，`T[]` 表示数组，未标可空的字段必填。内部不可变集合可用 tuple，JSON 使用数组。
- `schema_version="1.0"`；时间展示用 UTC ISO 8601，运行时期限用同一进程的单调时钟。日志保存相对请求接收的毫秒数；不能把重启前的单调时钟值作为新进程的期限。
- `Seat` 为整数 0—3，队友为 `(seat+2)%4`。`Stage` 为 `play | tribute | back`；内部 `back` 对应平台命令 `PAYTRIBUTE`。
- `Card` 保留平台牌面编码：普通牌为 S/H/C/D 加 2—9、T/J/Q/K/A，小王 `SB`、大王 `HR`。手牌是多重集合的数组表示，例如 `["S9","S9"]` 是两张牌，不生成臆造的实体牌 ID。扣牌按出现次数，不能用 set 相减。
- `run_id`：一次冻结配置的运行，UUID；`match_id`：一次创建/加入的比赛尝试，UUID；`round_id`：该比赛的小局序号，从 1 递增；`session_id`：该比赛某座位的 UUID。房间号单独保存在 `room_id`，不能代替这些本地 ID。
- `connection_epoch`：Session 每建立一条连接递增；首版断线中断，不重连旧局。`rx_seq`：该连接接收循环分配的递增帧号。两者不是服务器幂等键。
- `state_version`：Session 每应用一条影响决策的事实递增；`request_id="<session_id>:q<N>"`：有效本人请求的递增编号。`decision_id` 与 `request_id` 相同，一次请求只有一个决策账本。确认补记、日志、模型理由和 UI 轮询不改变 `state_version`。
- `RequestBinding={run_id,match_id,round_id,session_id,seat,connection_epoch,request_id,state_version}`。工具、模型、图结果、提交意图均携带它。完整字段相等且仍指向 Session 当前活动请求才有新发送资格。

### 8.2 局势与完整合法集合

| 结构 | 字段与类型 | 约束 |
| --- | --- | --- |
| `PublicPlay` | `event_id:str, seat:Seat, action:WireAction` | 只来自已应用的公开出牌通知；PASS 也可记录 |
| `VisibleState` | `binding:RequestBinding, stage:Stage, self_hand:Card[], level_rank:str, remaining_counts:(int?)[], team_ranks:(str?)[], turn_seat:Seat, leader_seat:Seat?, leading_action:WireAction?, finished_order:Seat[], history:PublicPlay[], history_complete:bool, history_omitted:int, facts_status:trusted或degraded` | `team_ranks` 固定 2 项；`remaining_counts` 固定 4 项，未知为 null；领先者与动作同时可空；历史只保留本小局；`history_complete=false` 包含因裁剪或缺失造成的不完整 |
| `WireAction` | 普通为 `[type:str, rank:str, cards:Card[]]`；PASS 为 `["PASS","PASS","PASS"]` | 作为适配层数据原样保留；不重排 cards，不把同牌组的不同类型解释合并；模型输出不能构造它 |
| `LegalAction` | `action_id:str, source_indices:int[], wire_action:WireAction` | ID 为首个原始下标生成的 `L0000`、`L0001` 等，最少补足 4 位；只在当前请求内有意义 |
| `LegalActionSet` | `binding:RequestBinding, raw_count:int, actions:LegalAction[]` | 按原始三元数组精确 JSON 值去重，记录所有原始下标；不排序数组后再去重；非空才允许处理 |
| `RequestContext` | `state:VisibleState, legal:LegalActionSet, received_at:str, fallback_action_id:str, policy:V0或V1或V2, platform_context:TributeContext?` | `fallback_action_id` 在完整集合中，建请求时先用廉价规则确定；单调时钟期限及可写计数只由 Session 保留，不向模型提供 |

`WireAction` 的 PASS 是平台的原始表示（当前快照为 `["PASS","PASS","PASS"]`），其中占位串不按 `Card` 校验或扣牌。当前贡还牌的 type/rank 分别是 tribute/tribute 或 back/back。非 PASS 的 cards 才逐项按牌码与本人多重集合检查；规则解释保持在平台适配与手牌模块，不扩展成全新的完整规则引擎。

唯一动作捷径检查的是**去重后的完整 `legal.actions` 长度为 1**，不是原始列表长度或筛选后长度。原始重复选项保留可追溯下标，不重复给模型。当前协议的 `indexRange` 是末下标，空列表也可能为 0，不能拿它代替长度；当前 WS 消息无 `numAction` 约定。

当前请求的 `handCards` 是本人权威快照；新请求可以替换本人手牌，但不能把当前快照当作整段公开历史已完整恢复。若其他事实冲突而当前动作请求自身仍能证明手牌、阶段和合法集合可信，标 `facts_status=degraded`，仅规则处理；请求本身归属不可信则中断，不能以“有 actionList”强行继续。

### 8.3 工具、候选与建议

| 结构 | 必填字段（可空项另标） | 约束 |
| --- | --- | --- |
| `ActionFeatures` | `played_count:int?, remaining_count:int?, estimated_turns:int?, single_count:int?, split_cost:float?, is_bomb:bool, finishes_hand:bool, beats_leader:bool, rule_score:float` | 未完成的复杂分析为 null；估计不等于最少手数；贡还牌的 played_count/remaining_count/estimated_turns/single_count/split_cost 设 null，三个游戏风险布尔值设 false，使用阶段专用 rule_score；不套用 PLAY 扣牌公式 |
| `Candidate` | `action_id:str, features:ActionFeatures, keep_reasons:str[]` | 沿用完整集合 ID，不重新从 0 编号；牌面与类型通过原映射生成模型/展示投影 |
| `CandidateSnapshot` | `binding:RequestBinding, candidate_snapshot_id:str, candidates:Candidate[], rule_action_id:str, tool_status:ok或degraded, degradation_codes:str[]` | ID 为 `request_id + ":c1"`；同请求最多注册一份，复核不可换候选；`rule_action_id` 是完整集合中的正常规则首选，可与最初廉价备选不同 |
| `DecisionInput` | `context:RequestContext, candidates:CandidateSnapshot?` | 唯一动作可没有候选快照；否则工具结果须先由 Session 核对 binding 并注册，才进入模型分支 |
| `ModelDecision` | `action_id:str, reason:str` | 严格且仅有这两个字段；ID 长度 1—80，理由 1—240 字符且去空白后非空；不得接受额外牌组或多个选择 |
| `ReviewResult` | `kind:review或repair, status:skipped或kept或changed或repaired或failed, trigger_codes:str[], before:ModelDecision?, after:ModelDecision?, call_id:str?, error:ErrorInfo?` | `changed` 由程序比较 ID 得到；修复前无有效主建议；未成功 begin_call 为 skipped（可已领票据，call_id 非空且占用名额不退）；成功 begin_call 后失败才为 failed，不能伪造复核启动/完成 |
| `DecisionProposal` | `binding:RequestBinding, candidate_snapshot_id:str?, action_id:str, source:unique或rule或main或review或repair或fallback, reason:str, cause_code:str?, review:ReviewResult?` | 模型来源必须属于登记候选；规则/兜底可以从完整集合选择；只提出建议，无发送能力 |
| `DecisionOutcome` | `status:proposed或invalidated或unavailable, proposal:DecisionProposal?, error:ErrorInfo?` | 仅 proposed 有 proposal；失败不伪装成一个 PASS |

候选必须保留：合法 PASS、**全部**可直接走完的动作、符合 F03 条件时至少一个压制选项。普通 Top-K 只控制其余项；必要项超目标可扩容到硬限制，超过硬限制或输入字节上限则返回 `CANDIDATE_OVERFLOW`，Session 使用廉价备选。一次工具处理超时/异常则直接降级规则，不为了凑候选重跑多个阶段。

### 8.4 错误与执行结果

`ErrorInfo={code:str, component:str, safe_message:str, related_event_id:str?}`；message 不带凭证、HTTP 请求头、供应商完整错误正文或任意对象 repr。预期故障用结构化返回值；意外异常在模块入口转换为 `INTERNAL_ERROR`，Session 仍决定有效请求下的兜底。不设通用 `retryable=true` 自动重试开关。

| 错误码组 | 处理 |
| --- | --- |
| `PROTOCOL_UNKNOWN / INVALID_REQUEST / EMPTY_LEGAL_SET / STATE_CONFLICT` | 不调用模型；请求信息独立可信时只规则处理，否则中断并保留证据 |
| `TOOL_TIMEOUT / ENGINE_UNAVAILABLE / CANDIDATE_OVERFLOW / TOOL_INVALID_RESULT` | 登记降级，当前有效请求用廉价规则备选 |
| `MODEL_TIMEOUT / MODEL_TRANSPORT / MODEL_EMPTY / MODEL_OUTPUT_LIMIT / MODEL_CONTENT_FILTER` | 主调用失败即规则兜底，不作为可修复输出 |
| `MODEL_SCHEMA / MODEL_ACTION_UNKNOWN` | V2 尚有第二次机会时允许一次 repair，否则规则兜底 |
| `CALL_BUDGET / BATCH_BUDGET / INPUT_LIMIT / NO_REVIEW_TIME` | 不发起本次调用；复核尚未开始且主建议有效时保留主建议，否则规则处理 |
| `REQUEST_STALE / DEADLINE / CONNECTION_CLOSED / ALREADY_RESERVED` | 拒绝新提交；不发送旧备选 |
| `SEND_UNKNOWN / CONFIRM_TIMEOUT / UNMATCHED_FEEDBACK` | 保留已发送或可能已发送的记录，不重发；可靠迟到反馈可补记 |
| `LOG_INCOMPLETE / INTERNAL_ERROR` | 记录/展示缺口；根据当前请求有效性决定能否兜底，不掩盖中断 |

`ExecutionRecord` 字段为 `submission_id:str, binding:RequestBinding, action_id:str, wire_action:WireAction, source:str, status:str, reserved_at:str, write_started_at:str?, sent_at:str?, confirmed_at:str?, feedback_event_id:str?, error:ErrorInfo?`。

状态为 `reserved → writing → sent → confirmed`；`reserved → cancelled_before_write`；`writing/sent → unknown`；可关联的明确拒绝为 `rejected`。`unknown → confirmed/rejected` 需要新的可靠平台证据。网络写出完成前也可能先收到接受通知，因此 `writing → confirmed` 合法，之后发送完成事件不得把状态退回 sent。当前平台尚无已验证的动作拒绝消息，`rejected` 保留给可证明关联的反馈，不能用普通 code=-1 猜测。

`request.status`（active/invalidated/closed）与提交状态分别保存：请求截止不抹掉 sent/unknown 记录。`closed` 表示不再生成建议，不等于动作已确认；每请求最多一个 submission_id，取消或未知后也不自动重提。

## 9. 平台协议映射与状态更新

本节仅适用于本地官方快照 `e92db7fa9d915fb318b3be78703d5ccd4a09c887`。归属从连接绑定补足；`act/notify` 通常没有 roomId、服务器请求号、小局号或事件号。不能把本地编号描述为服务器保证。

### 9.1 接收映射

| 原始 type / stage | 关键字段 | 规范化事件与处理 |
| --- | --- | --- |
| CREATE_ROOM / JOIN_ROOM | code、data.roomId、data.userNum、错误 data.msg | `joined` 或 `join_failed`；userNum 为本连接座位，和后续 myPos 核对；JOIN 只是有人加入的公告 |
| notify / beginning | myPos、handCards、levelCard | `round_started`；使旧请求失效，生成下一 round_id，按下文初始化全部局内事实；当前级牌取 levelCard |
| act / play | handCards、publicInfo[].rest、selfRank/oppoRank/curRank、curPos/curAction、greaterPos/greaterAction、actionList | `action_requested(stage=play)`；接收座位为本次行动者，**不是 curPos**；本人手牌与合法集合建立请求，公开张数按座位索引；rank 映射见下文 |
| act / tribute | handCards、三个 rank、actionList | `action_requested(stage=tribute)`；公开张数可能缺失，只沿用本小局已确认事实或 null，不沿用上一小局张数 |
| act / back | 上述字段、tributePos、tribute | `action_requested(stage=back)`；保留目标座位和原进贡牌至 RequestContext.platform_context，提交时原样回传 |
| type=tribute，无 stage | code、data.actionList（对象映射） | `auxiliary_notice`，仅展示；它不是可直接选择的三元动作数组，等待 act/tribute |
| notify / play | curPos、curAction、greaterPos、greaterAction | `play_observed`；curPos 为刚出牌者，仅此事件应用一次扣牌/公开历史；greater 字段是更新前状态，不覆盖成当前领先状态 |
| notify / tribute | result=[[进贡者,接收者,牌],…] | `tribute_announced`；确认选择及配对，缓存贡牌，不立即换手牌 |
| notify / back | result=[[还贡者,接收者,牌],…]、count | `exchange_completed`；结合贡牌缓存一次应用本人交换；count 仅是当前接收座位的手牌数 |
| notify / anti-tribute | antiNums、antiPos | `anti_tribute`；不发生交换，等待出牌请求 |
| notify / episodeOver | order、curRank、restCards | `round_result`；结束当前小局，记录排名；restCards 为事后披露，单独保存，不能回填历史决策快照 |
| notify / gameResult | victory、victoryRank、victoryNum、gameResult、gameRound | `match_result`；victory=0 为 0/2 队获胜，1 为 1/3 队；保留原字段，不把 gameResult 数组当四人得分 |
| notify / gameOver | curTimes、settingTimes、gameRound | `match_closed`；关闭本场；不能单凭它猜胜方或小局数 |
| 其他/字段类型异常 | 原始消息及安全错误 | `unknown`；不作为动作请求。影响当前阶段可信性则停止，否则只保留诊断记录 |

各规范化 kind 的 payload 使用该行列出的原始字段，适配器负责类型验证，不默认补缺失必需字段；`action_requested` 另外带内部 stage、无 binding 的 `ParsedActions={raw_count:int,actions:LegalAction[]}` 与 `TributeContext?`。Session 验证后加入 binding/状态版本，将 ParsedActions 包装为 LegalActionSet；适配器不生成另一套权威 state。`TributeContext={tribute_pos:Seat,tribute_card:Card}` 仅 back 必填，其余为 null；两字段也可作为当时已知信息投影给模型。

`VisibleState.team_ranks` 为座位 0/2 队、1/3 队顺序的两项 rank，可空。按本座位奇偶把 selfRank/oppoRank 映射进去；本局实际级牌用 curRank（开局用 levelCard），不能把“本队升级到哪里”直接当当前级牌。act.curAction 是上下文，可能重复刚刚的 notify/play，**不再扣牌或追加公开动作**。act.greater* 是该请求时领先状态，覆盖当前决策快照；首出 `greaterPos=-1 / greaterAction=null` 以及空/PASS 哨兵成对规范化为 null。通知之间页面可以保留最近公开出牌，但不能从旧 greater* 猜出新请求的领先者。

**新小局初始化是替换局内状态，不是只替换手牌。** 收到可信 `beginning` 时，在一次 Session 处理内执行以下规则：

| 对象 | 新小局处理 |
| --- | --- |
| 手牌、数量和级牌 | `self_hand=handCards`；`remaining_counts` 四项先置 null，再令本人项等于新手牌长度；`level_rank=levelCard`；`team_ranks=[null,null]`，待本座位下一 act 的 selfRank/oppoRank 刷新 |
| 局内公开事实 | `finished_order=[]`、`leader_seat=null`、`leading_action=null`、`history=[]`、`history_omitted=0`；展示阶段设 waiting；清空旧贡还缓存及模型猜测 |
| 完整性 | 从此次可信开局起事件连续且尚无缺失/裁剪时，`history_complete=true`；未知其他座位张数本身不构成冲突。新开局不能恢复已中断连接或抹除此前日志缺口 |
| 活动决策 | 旧请求失效，解除活动候选/主建议登记，撤销旧票据的开始资格和未写出意图，取消其决策任务；旧计时器按 binding 失效，不作用于新局 |
| 保留的资料 | 比赛/Session/连接身份、比赛级记录与批次已占额度继续保留；state_version、view_version、请求序号 q 和 rx_seq 保持递增。历史决策账本、call_id 去重、迟到用量及已写出/可能写出的提交索引不能删除；旧确认仅补历史证据 |

已知剩余张数收到本局非 PASS 出牌通知才扣减，未知项保持 null，不能按零或旧小局值做减法；下一 act.publicInfo 再以当前权威张数覆盖。`act.curAction` 仍只作上下文，不重复扣牌或记录历史。局内事实恢复可信不代表整场证据已经完整。

同一比赛的各座位 round_id 依各自收到的 beginning 次序建立；RunManager 只协调比赛/小局编号，不汇总私牌。离线聚合同一 round_id 时需核对各流没有缺失/错序；有缺口不能把后面的相同编号强行对齐。

### 9.2 发送映射

以下是独立格式例子，必须用对应有效请求的原始动作替换，不能作为连续命令直接发送：

```json
{"type":"CREATE_ROOM","data":{"userId":"p0","round":1,"seatNum":0}}
{"type":"JOIN_ROOM","data":{"userId":"p1","roomId":1,"seatNum":1}}
{"type":"PLAY","data":{"roomId":1,"player":0,"act":["Single","B",["SB"]]}}
{"type":"PLAY","data":{"roomId":1,"player":0,"act":["PASS","PASS","PASS"]}}
{"type":"TRIBUTE","data":{"roomId":1,"player":0,"act":["tribute","tribute",["SA"]]}}
{"type":"PAYTRIBUTE","data":{"roomId":1,"player":0,"act":["back","back",["D2"]],"tributePos":2,"tribute":"SB"}}
```

`player` 固定为本连接已确认座位；`roomId` 来自成功入局；`act` 用 source_indices 对应的完整原数组，不发 action_id 或数组索引。PAYTRIBUTE 的附加字段取同请求 TributeContext，不能由模型决定。创建的 round=1 在实测中是一整场升级赛，不是一小局；首版固定 1，批次由运行管理逐场新建，等待四个参赛者入局后由服务器开始。

### 9.3 确认、交换和去重

| 提交阶段 | 接受证据的最小匹配条件 |
| --- | --- |
| play | 对应比赛/连接/小局的待确认记录；notify/play 的 curPos 为本座位；curAction 的牌型和声明级别相同，牌组多重集合相同；PASS 三项完全相同 |
| tribute | 对应本小局贡牌阶段；notify/tribute 的一行进贡者为本座位，牌为提交的唯一牌，该行确定接收者 |
| back | 对应本小局还贡阶段；notify/back 的一行还贡者为本座位，接收者等于本请求 tribute_pos，牌等于提交还贡牌，并与本阶段贡牌配对一致 |

匹配前须有唯一可关联的 writing/sent/unknown 记录，接收序列/阶段连续且时间顺序不冲突。内容相同本身不能关联任意历史提交。阶段三贡还牌探针实际匹配“阶段、发出座位、牌”；本节额外加入接收者、配对和请求归属。B03 已实现这些增强检查并通过本地场景；B04 已从本次新客户端的原始通知核实 992 条确认链，实际范围见实施计划第 7.6 节。

换牌时点：`notify/tribute` 只公告配对；`act/back.handCards` 仍是交换前牌。收到 `notify/back` 后，按贡与还的转移表计算本人的出入多重集合，一次应用，再核对 count 和下一次 act.handCards。缺少转移、重复扣到负数或计数冲突，标 STATE_CONFLICT；不得自行凭猜测修手牌。抗贡跳过交换。新 beginning 到来使旧交换缓存失效；旧确认只能补历史执行证据。

去重仅覆盖可证明同源的事件：同 connection_epoch/rx_seq 被内部重复投递、同 submission_id 重复回调。不同网络帧即使 JSON 相同也不凭内容去重；可解释的后续同值出牌仍正常应用。新请求在无合理阶段推进时重复出现，不重置调用预算“重跑一次”，而是标为状态不可信、停止当前建议并核对；当前平台无恢复接口时中断。不存在用“座位+牌面”永久去重的规则。

## 10. 模块调用与并发契约

### 10.1 最小调用面

以下是 Python 风格签名约定；`async` 方法可以等待外部工作，但 Session 处理入口不能等待完整模型或工具任务。通过构造参数注入平台、模型、时钟、记录器；无需通用插件系统。

| 所有者 | 接口 | 返回/副作用与失败约定 |
| --- | --- | --- |
| M01 `RunManager` | `start(config:RunConfig) -> RunView`；`stop(run_id:str) -> RunView` | 先验证并冻结配置；首版同一时刻仅一场比赛；重复 start 为 RUN_CONFLICT，stop 幂等；下发给各 Session，不直接猜结算 |
| M02 `PlatformPort` | `async connect(config:SeatConnection) -> None`；`events() -> AsyncIterator[PlatformEvent]`；`async write(intent:SubmissionIntent, gate:SendGate) -> SendResult`；`async close() -> None` | 每连接一个接收者，持续产生日志归属明确的事件；write 只能用 Session 意图，实际写出前通过受限 SendGate 同步复查请求、占用、连接和期限；真实和脚本平台实现同一接口 |
| M01 `Session` | `post(event:SessionEvent) -> None`；`view() -> SessionView` | post 在同一事件循环中立即完成短的同步状态更新，返回即已应用；重任务另行调度；view 返回状态副本，不触发决策 |
| M03 `HandTools` | `cheap_choice(state:VisibleState, legal:LegalActionSet) -> str`；`async prepare(context, limits:ToolLimits) -> ToolResult` | cheap_choice 确定备选后才构造完整 RequestContext；prepare 返回 `ToolResult={snapshot:CandidateSnapshot?,error:ErrorInfo?}`；不写 Session，不发送动作，不访问其他座位 |
| M04 `DecisionPolicy` | `async decide(input:DecisionInput, calls:CallPort) -> DecisionOutcome` | 唯一/V0 为程序分支，V1/V2 使用图；输入候选已登记；返回建议/作废，不能自行写 WS |
| M05 `ModelGateway` | `async choose(input:ModelInput, calls:CallPort) -> ModelCallResult` | 等全局并发名额、申请调用票据、执行一次模型传输、解析并回传结果；无隐藏重试，必须尊重剩余期限 |
| M05 `ProviderPort` | `async complete(input:ProviderInput) -> ProviderReply` | 共享的单次供应商传输；不接收 CallPort/游戏 binding，不作动作或报告语义校验，不排额外业务队列、不自动重试；真实与脚本实现同一接口 |
| M06 `EventStore` | `async create(run_dir,run_id,config,clock,...) -> EventStore`；`append(draft:EventDraft) -> AppendResult`；`query(scope:EventQueryScope, after_seq:int, limit:int) -> EventPage`；`async close(run_id,...) -> RunSummary` | create/close 的文件工作在同步 Session 入口之外等待；append 不等待磁盘；close 有限等待并返回完整性标志；query 不触发模型或发送 |
| M08 `Evaluator / Reviewer` | `evaluate(run_ids) -> EvaluationReport`；`async review(run_id, limits) -> ReviewReport` | 通过 run_id 读取已关闭运行的配置、日志和汇总；报告另存，复盘调用独立预算；不修改源记录和在线配置 |

**在线与离线共用传输，分别授权和校验：** `ProviderInput={call_id:str,messages:[{role:system或user或assistant,content:str}],deadline_mono:float,max_output_tokens:int}`；实际模型与凭证由 M05 运行时配置注入，不放入消息或返回对象。`ProviderReply={call_id:str,content:str?,usage:Usage,transport_requests:int?,elapsed_ms:float,error:ErrorInfo?}`。它只返回原始文本，不要求 action_id、候选、RequestBinding 或在线票据；上层先执行输入大小限制。JSON 输出模式沿用现有 DeepSeek 接入，不引入供应商注册框架。

在线 ModelGateway 负责候选/ModelDecision 校验，并严格沿用第 10.3 节的并发名额、CallPort 和 begin_call；只有 allow 后才能立即进入 ProviderPort。ProviderPort 不再插入业务等待，SDK 网络等待计入剩余期限，自动重试为零。离线 Reviewer 从已关闭的对局记录组织提示词，由 RunManager 在单调期限内检查离线任务仍有效、无在线比赛、额度/输出上限足够，再占用独立名额并立即调用 ProviderPort；该路径不接触在线 slots 或发送权限。B 在 P12 交付 ProviderPort，C 在 P19 对其接入；A 维护公共结构和运行管理的授权接口。

B05 将本地传输任务与等待方分开：begin_call 在传输任务内紧邻 complete 执行；等待方到期后及时返回，但未真正结束的任务继续持有并发名额，完成回调只释放一次。迟到回调最多补原 call_id 的未知用量/传输计数，不恢复已失败的 decision。RunManager 按 run 创建共享工具、预算、Gateway/Provider，并在 Session 关闭后统一清理；跨座位和多场不重置额度。ScriptedProvider 同样自行执行 deadline，不能依赖在线 Gateway 替离线路径兜底。

取消/超时先结束本地等待并尽力取消传输，不重试。实际已发尝试仍计数，无法确认的用量为 null；取消不能证明远端未执行/不计费。新在线 run 使受管理的离线任务失效，不等待远端结果；离线任务尚未结束时，可观测的迟到用量只归入原 call_id；任务关闭后保留未知值，不做补充证据版本链，也不恢复生成或占用在线额度。常规传输错误以 ProviderReply.error 返回；协程取消可传播 CancelledError，由在线/离线调用者记录取消与当时可获得的计数，不把取消当成功回复。失败与取消均不输出供应商请求头或密钥。

`ToolLimits={deadline_mono:float,deep_eval_limit:int,candidate_target:int,candidate_hard_limit:int}` 的 deadline 由 Session 取工具预算与 t_suggest 的较早者；`AppendResult={accepted:bool,seq:int,event_id:str,error:ErrorInfo?}`。`ToolResult={snapshot:CandidateSnapshot?,error:ErrorInfo?,elapsed_ms:float?}` 的 snapshot/error 至少一项存在，带降级特征但可用的 snapshot 可以附诊断错误；结构异常不得登记。RunConfig 即第 12.3 节嵌套配置结构，冻结后只读。

`SessionEvent` 的完整目标包括 `PlatformEvent / ToolsReady / MainReady / ProposalReady / SuggestionDeadline / SubmissionDeadline / CallFinished / WriteStarted / SendFinished / ConfirmationDeadline / Stop / ConnectionLost`。B03 实现规则闭环事件，B05 已增补 ToolsReady、MainReady 与 CallFinished，并由同步 CallPort 记录调用完成后再登记主建议。所有请求级异步结果携带 binding；计时器不能只凭 seat 修改后来请求。停止与断线携带 run_id/session_id 和安全原因，不伪造请求 binding。`ToolsReady` 注册成功才启动 decide；图中“工具节点”可由策略外壳完成，不要求在 Graph 内等待 Session 锁。`MainReady={binding,candidate_snapshot_id,call_id,decision:ModelDecision,trigger_codes:str[]}` 用于登记有效主建议；登记规则见第 10.3 节。

平台、运行和结果结构的补充：

- `SeatConnection={url:str,mode:create或join,room_id:int?,user_name:str,seat:Seat,session_id:str,connection_epoch:int,server_rounds:int}`；user_name 映射必需的 userId。create 时 room_id=null、server_rounds=1，创建成功后 RunManager 将 roomId 传给其余 mode=join 的座位，join 的 room_id 必填；连接成功仍需 CREATE_ROOM/JOIN_ROOM 响应成功才标入局。
- `PlatformEvent={session_id,connection_epoch,rx_seq,received_at,received_mono:float,kind,payload,raw_message:object?}`；kind 为第 9 节事件。B03 增加 raw_message 保存成功解析帧的原始 JSON 值，用于本座位证据，不保证字节/空白格式一致；非 JSON 坏帧保留在 unknown.payload 的诊断字段。received_mono 只供进程内预算使用，日志转换成相对耗时；原始消息按座位归属记录，策略只取显式白名单后的 VisibleState，不接收 PlatformEvent。
- `SubmissionIntent={submission_id,binding,action_id,wire_action,stage:Stage,platform_context:TributeContext?,final_deadline_mono}`，只在进程内存在，不接受 UI/模型提供；back 的 platform_context 必填且来自同请求冻结副本，其他为 null，适配器不另查可变 Session。`SendResult={submission_id,status:sent或not_started或unknown,error:ErrorInfo?}`，发送返回不直接扣牌。
- `RunView={run_id,status:starting或running或stopping或completed或interrupted,config_id,active_match_id:str?,sessions:[{session_id,match_id,seat,status}],log_complete:bool,error:ErrorInfo?}`。error 提供安全启动/中断原因。`SessionView` 是 UI 投影，见第 12 节。未写日志不等于比赛未结算，两者独立。

B09新增独立离线能力：`start_review(config,source:ClosedRunLog,job)->OfflineTaskView`、`review_view(task_id)`、`await wait_review(task_id)->ReviewReport`、`stop_review(task_id)`、`offline_usage()` 与 `await close_reviews()`。job只接收 `OfflineCallPort={task_id,async call(messages)->ProviderReply}`，不创建在线binding/Session。`OfflineTaskView={task_id,source_run_id,status:running或completed或partial或failed,slots_used,calls_started,calls:OfflineCallRecord[],error?,report_ready}`；每条OfflineCallRecord含call_id、started/transport、elapsed_ms、usage/error，没有动作权限。

离线model/offline/提示配置首次冻结，同Manager后续任务不补额；每任务只调用一次生成器。新online run在有效启动时同步停止未完成offline，停止后报告与用量冻结。限时清理不承诺远端零费用。默认CLI `review CONFIG SOURCE...` 仅检查，显式 `--live` 才生成；`evaluate SOURCE...` 为纯程序统计。生成文件独占新路径，不覆盖config/events/summary或已有报告。

### 10.2 接收、版本及提交 gate

首版采用同一事件循环内的**短同步状态入口**，不建立 Session 业务收件箱，也不维护入队/应用双序号。日志写入缓冲和 WebSocket 底层缓冲不承担 Session 事实排序职责。

1. 每个连接只有一个接收循环。取得原始帧后记录 received_mono/rx_seq，完成同步解析并立即调用 `Session.post(event)`；接收到帧至应用事件之间不另作业务等待或派发第二个消费任务。post 返回时，该事件已经更新状态。
2. post、MainReady 登记、调用/发送关口都在同一事件循环中执行短同步操作，不 await、不递归调用 post、不运行 Java 或其他耗时计算。工具、模型和文件 I/O 在外部任务中等待，完成后回到此入口；HTTP 停止入口同样立即应用 Stop，再返回响应。工作线程不能直接修改 Session。
3. 有效本人请求应用事实、递增版本、建立 binding，准备廉价备选和两个计时器。非唯一请求另起工具任务；结果仍属于当前请求时登记一次候选并启动策略。只影响日志/用量的旧事件不修改当前决策事实。
4. 新请求、相关事实变化、Stop、断线或结算立即使旧请求失效，关闭旧票据的开始资格并取消未写出的提交意图。工具、MainReady 和最终建议到达时，直接复查 binding、suggestions_open 和 `now<t_suggest`；过期结果不能恢复资格。
5. 决策结果和 watchdog 共用一个提交入口。检查当前 binding、动作来源、阶段、期限及无已有 submission 后，原子建立 reserved 记录。预登记 main 不占提交机会。等待发送通道发生在外部发送任务，不能卡住 Session。
6. 适配器取得发送通道后，紧邻 socket send 同步调用 `gate.begin_write(intent)`。关口重新检查活动请求、submission 归属、连接代次、阶段和最终期限；允许则原子标 writing，随后立即开始网络写出，中间不再业务排队。已经进入本地接收/停止入口的事件此前已同步应用，因此不会跨过一条“入队但未处理”的失效事件。
7. 未开始写出时失效，返回 deny 并取消意图；writing 后错误或取消可能已经发送，保留 unknown 和占用，不重发。一次请求最多一个提交决定，模型迟到不能替换已提交动作。
8. 运行尚未关闭时继续匹配已发送动作的可靠反馈，补记确认但不重复扣牌或覆盖新局。最终提交截止只禁止新发送，不抹去原提交记录；运行关闭时仍未确认的保留 unknown。

`GateDecision={status:allow或deny,error:ErrorInfo?}`。`SendGate` 只提供同步 `begin_write(intent)`；删除 defer、until_seq 和 wait_applied。这里同时改变事件入口与关口契约，不能保留旧的异步收件箱却只删除等待检查。T05/T12/T13 验证同步事件顺序、旧绑定拒绝及一次提交，具体见第 13 节。

本设计保证本地已处理事实下的一致性；尚未送达或尚未被接收循环取出的服务器消息不能凭本地推断。取消异步任务不是安全保证，最终版本/期限检查始终保留。

### 10.3 两个截止与一次调用票据

`t0` 为接收请求的本地单调时间；`t_final=min(t0+decision_total_s,可可靠换算的平台期限)`，未知平台期限时标 local_experiment；`t_suggest=t_final-submit_reserve_s`。解析、工具、并发等待和模型都计入同一次预算。

- 有效主建议通过同步 `register_main(MainReady)->bool` 登记。Session 检查 binding、候选、期限，且 call_id/decision 对应本请求已完成的有效主调用；成功保存 registered_main。Graph 在登记成功后才允许 review，失败则按当前请求/截止状态交回 Session。登记不发送动作。
- 建议截止关闭 suggestions_open 并取消未完成任务。请求仍有效、无提交且尚未到最终截止时：有已登记有效 main 且 second_call_started=false，采用 main；否则采用廉价备选。第二次是否开始只由 review/repair 的 begin_call 成功步骤同步置位，主调用不能置位。
- 截止保留 main 时 source=main；本应战术复核但未开始则记 skipped，没有复核需求则 review=null。第二次已开始但未得有效最终结果时用 fallback，记失败；主输出无效且 repair 未开始时仍用 fallback。两者的统计不得混淆。
- 模型等待不超过 `min(model_timeout_s,t_suggest-now)`。复核启动须有第二次名额和至少 review_min_remaining_s；并发排队后还要重新检查。到 t_final 禁止任何新写出，写入超时按 unknown，不再另发备选。
- 确认等待从 writing 起算 confirm_timeout_s，超时标 unknown；运行关闭前可靠迟到反馈可补记，关闭后不提供自动追溯修订。

B07 已实现 `ReviewResult` 的字段一致性和 Session 调用来源核对。`kept/changed` 必须有有效 before/after 且由编号比较确定；repair 的 before=null，成功为 repaired；skipped/failed 的 after=null 且必须有安全错误。`failed` 必须对应已开始的 call_id；skipped 可保留已占用但未开始的票据。带第二次结果的 fallback 也携带同一候选快照编号，保留原失败原因。`review_finished` 在本请求首次产生终结建议/保底提交时只记录一次，包含 binding、candidate_snapshot_id 和 ReviewResult；它不代表服务端确认。

`CallPort` 仅暴露同步的 `status(binding)->BudgetView`、`register_main(main)->bool`、`admit_call(binding,role)->CallTicket或ErrorInfo`、`begin_call(ticket)->GateDecision` 和 `record_result(result)->None`。`BudgetView={active:bool,suggestions_open:bool,remaining_s:float,slots_used:int,max_slots:int}` 为瞬时观测。模型 Gateway 先在剩余时间内异步取得全局并发名额，再同步申请/消费票据并立即调用 ProviderPort；Session 从不等待并发名额。

`CallTicket={call_id,binding,role:main或review或repair,ordinal:int,deadline_mono:float}`。admit_call 在短同步步骤中检查请求和批次额度并占用一次名额；begin_call 再查当前 binding、期限和票据未使用，allow 才标 calls_started，第二次角色才置 second_call_started。失败名额不回补，单票不能重用；Gateway 关闭自动重试。record_result 在 choose 返回前同步记录 CallFinished，因此随后 register_main 能读取该结果，无需事件回执等待。

保留 slots_used、calls_started 与可观测的 transport_requests，区分保守占用、开始调用和实际传输。每请求 V0/V1/V2 上限 0/1/2，失败也计入；用量缺失为 null。运行关闭前可补当时获得的用量，关闭后不为收齐遥测持续运行任务，也不能把未知算成免费。

### 10.4 工具工作进程

工具总时限覆盖候选排序和 Java 分析，仅深评配置上限内的候选，Java 只接收本人余牌与规则参数。初版不要求专门缓存或自动重建管理器；确有性能需求时再评估缓存，不能共享其他座位私牌。

工作进程一次只处理一个调用。超时或故障时停止派发，本请求使用廉价备选；后台执行有限的 terminate/kill 与管道清理，本次 run 标记该分析器停用，不等待旧调用返回、不在场内自动重建。以后请求仍可用廉价特征准备合法候选，并标 tool_status=degraded；无法准备有效候选才转廉价备选。下次显式启动新 run 时重新初始化分析器。

迟到工具结果按请求绑定丢弃。保留超时和必要清理的验证，自动恢复、进程代次切换及复杂缓存压测移到后续扩展；完整 Python Table 不进入正式依赖。

## 11. 模型输入与 LangGraph 分支

`ModelInput={binding,candidate_snapshot_id,role,visible:VisibleState,candidates:ModelCandidate[],platform_context:TributeContext?,main:ModelDecision?,trigger_codes:str[],validation_error:str?}`。Gateway 将 visible 显式白名单投影，不把 binding、run 配置、密钥、原始帧、其他 Session 或供应商对象送入提示。ModelCandidate 只含 `action_id,type,rank,cards,features,keep_reasons`，来自已登记映射；PASS 的模型投影 cards=[]，原 wire 的三项 PASS 表示仍在合法集合中保留。完整 legal 不传给模型。binding 由程序绑定结果，不能相信模型回传的请求号。模型投影显式补入本请求的 TributeContext（可空），不传入其余平台原始字段。

主调用和第二次调用都只返回以下 JSON（字段名和输出示例必须出现在提示词中）：

```json
{"action_id":"L0001","reason":"队友领先，先保留控制牌。"}
```

采用已验证的 ChatDeepSeek JSON mode（阶段三通过 `with_structured_output(..., method="json_mode", include_raw=True)` 验证）。B05 Provider 显式传 `response_format={"type":"json_object"}` 保留原始文本和用量，ModelGateway 执行本地严格 ModelDecision schema 与候选成员校验；`max_retries=0`，关闭自动 tracing。HTTP Mock 验证请求参数与重试行为；B06 已用新版实现取得一次真实供应商回复及对应平台动作确认。该样本的牌型理由描述存在误差，结构与合法编号校验不保证解释正确。只记录输出简短理由，不记录完整思维链。禁止在 parser 内补一次“自动修 JSON”请求。错误分支依据第 8.4 节；原始空字符串为 MODEL_EMPTY，非空且格式/字段错误为 MODEL_SCHEMA。

B07 默认提示版本为 `b07-review-v1`，按 main/review/repair 投影；复核增加有效 main 与风险码，修复只增加 `MODEL_SCHEMA` 或 `MODEL_ACTION_UNKNOWN`，不带原始错误文本。新增简短官方牌型释义以纠正 B06 观察到的描述歧义；旧 `b05-main-v1` 主提示字节保持，可供 V0/V1 历史配置使用，V2 必须用新版本。角色上下文不合法时返回 `INVALID_REQUEST`，不消费调用票据。

策略配置（risk 阈值、提示版本）从冻结 RunConfig 注入，不能在图中重新读 .env 或可变配置。Graph 状态只含 `input,main_result,trigger_codes,review_result,proposal,error`；调用计数/截止只有只读观测，真实权限在 CallPort。固定有向流程为 `main → route → review或repair或finalize或fallback → END`；route 对有效主建议先计算风险并确认 MainReady 同步登记成功，无效主建议不登记，无回边；唯一/V0/准备失败由策略外壳直接返回对应结果。风险码与默认规则：

以下三个战术触发器仅作用于 play 阶段；不基于贡还阶段的残缺张数发起战术复核。

| 风险码 | 第一版判定 |
| --- | --- |
| `OPPONENT_NEAR_FINISH` | 任一未出完对手的公开剩余张数为 1 或 2；未知不当成 0 |
| `USE_BOMB` | 主建议的已解析平台类型为炸弹或同花顺等炸弹类，类型映射随规则版本保存 |
| `BEAT_PARTNER` | 当前领先者为队友且主动作是非 PASS 的合法压制动作 |
| `SPLIT_COST` | B07 未验证阈值，保持关闭且配置拒绝非 null；以后须先定义/验证评分与阈值再开放 |

V1 有效主建议登记后 finalize；V2 有效主建议先登记（含风险码），有风险且票据/时间足够才 review。V2 的可解析性/候选错误只可 repair 一次，服务失败/超时不 repair。复核未真正开始且预算不足保留有效主建议；复核已经 begin_call 后出错用最初廉价备选；并发排队超时、尚未成功 begin_call 的情况属于 skipped；已领票据也不改变这个判定。如果已经到 t_suggest，不再靠 Graph 返回 main，而由 Session watchdog 使用此前已登记的 main；迟到 Graph 返回仍丢弃。第二次输出仍无效直接 fallback；多个风险合并，repair 后不再 review。任何分支发现请求失效，都返回 invalidated，不能“用备用补一手”。

## 12. 日志、界面、配置与离线报告

### 12.1 事件账本及分页

`EventDraft={schema_version,run_id,match_id?,session_id?,seat?,round_id?,request_id?,event_type,payload}` 由模块提交；记录器在短同步入口为每个通过结构校验的 draft 分配 seq/event_id/recorded_at，生成 `LogEvent={schema_version,event_id,run_id,match_id?,session_id?,seat?,round_id?,request_id?,seq,recorded_at,event_type,payload}`，再入有界写队列。队列拒绝仍返回已分配 ID 和 accepted=false，以便引用缺失证据并报告序号缺口。`seq` 在单个运行的统一写入器中递增，`event_id="<run_id>:e<seq>"`；丢失事件可留下序号空洞。引用使用 event_id/request_id，而非文件行数。

| event_type | payload 最少内容 |
| --- | --- |
| `run_started / session_started` | 脱敏冻结配置、config_id、源码/规则/适配器版本、环境、房间与座位归属；seed 不可控制则 null |
| `platform_received` | connection_epoch、rx_seq、原始本座位消息、规范化 kind、解析结果；凭证不在协议记录中 |
| `request_opened / request_invalidated` | binding、VisibleState、完整 LegalActionSet、廉价备选、预算参数与来源；失效原因及对应事件 |
| `candidates_prepared` | CandidateSnapshot、准备耗时、降级原因、输入裁剪量 |
| `model_call_started / model_call_finished` | call_id、role、ordinal、请求/候选关联、实际模型与提示版本、等待/传输耗时、计数、解析结果或安全错误 |
| `main_registered / proposal_ready / review_finished` | 登记绑定与 call_id、建议、风险码、主/复核 ID、修改/跳过状态；理由为模型判断；main_registered 不代表已提交 |
| `submission_reserved / write_started / send_finished / execution_updated` | ExecutionRecord、确认所用原始 event_id；保留每次转换，不原地覆盖 JSONL |
| `round_result / match_result / session_interrupted` | 平台原始结算、确定的归一结果或未知、证据引用；不能从本地停止推断输赢 |
| `log_gap / run_closed` | 缺失范围（可得时）、原因、最后持久化 seq、关闭状态及未确认提交；run_closed 由记录器最终写入 |
| `match_completed / run_finished` | RunManager 的协调完成/终止事件，保持与每席平台 match_result、记录器 run_closed 分开；不能据这些协调事件另计一场结果 |

`ModelCallResult={binding:RequestBinding,candidate_snapshot_id:str,role,call_id:str?,decision:ModelDecision?,error:ErrorInfo?,elapsed_ms:float,queue_wait_ms:float,calls_started:int,transport_requests:int?,usage:Usage,input_bytes:int?,history_omitted:int?}`。B05 增加 binding/role/snapshot 归属，Session 逐项核对原票据后记录；输入字节和裁剪量未知时为 null。`Usage={input_tokens:int?,output_tokens:int?,total_tokens:int?,cost_amount:float?,currency:str?,cost_basis:str?}`。准入失败而尚无票据时 call_id=null、calls_started=0、transport_requests=0，错误返回但不伪造 model_call_started。缺失用量为 null，0 只表示可证明为零；usage 返回不全不自行相加成完整总数。报价估算要保存价格来源、版本/日期与估算标识，不能把估算写成实付。

运行目录含 `config.json`、`events.jsonl`、`summary.json` 与 `reports/`。事件带 seat，在线查询强制座位过滤；原始四座位合并文件仅本地离线读取，不通过一个 GET 返回给在线策略。一个 writer 管有界队列，写失败时内存 health 立即 `log_complete=false`，恢复后尽力写 gap；无法写缺口本身时仍显示不完整。进程崩溃缺少关闭记录/汇总时标不完整，不补造结果。

`EventPage={items:LogEvent[],next_after_seq:int?,has_more:bool,retained_from_seq:int,log_complete:bool}`。按过滤后 seq 升序、`seq>after_seq`，不使用易漂移的页码；limit 默认 50、最大 200。首版使用有界内存列表/索引；历史文件首次打开时加载一次，暂不建设专门的磁盘索引系统；超过窗口而无可用索引返回 `410 HISTORY_UNAVAILABLE` 和最早可查 seq，不能悄悄跳过。游标只表示浏览位置，不恢复执行；普通 GET 不反复从头扫描 JSONL。

B02 的 `EventQueryScope={run_id,session_id,seat}` 三项均必填；查询先按三项一起过滤，不提供在线全座位查询。模块抛出的 `HistoryUnavailable` 在后续 HTTP 层映射为 410。读取既有文件使用独立的只读加载入口；缓存已截断时，全量离线读取方法必须明确拒绝或报告截断，不能把尾部窗口当整场记录。

### 12.2 最小 HTTP 接口

所有路径以 `/api/v1` 开头。默认只监听 `127.0.0.1`，同源页面访问；只挂载 `web/static/`，不得挂载项目根、.env、运行日志目录；此阶段不承诺账号、多用户或公网部署。POST 只接受 JSON，校验同源 Origin/Host，不开放通配 CORS。页面控制只传本地配置名，不能提交任意磁盘路径、供应商 URL、密钥或游戏动作。

| 方法与路径 | 输入 | 响应/行为 |
| --- | --- | --- |
| `GET /configs` | 无 | `200 {items:[{config_name,policy,model_calls}]}`；只读服务端启动时冻结的允许配置，不返回路径/凭证 |
| `GET /runs` | 无 | `200 {items:RunListItem[]}`；RunView 加 read_only/label，无手牌；label 只是配置元数据，不证明数据来源 |
| `POST /runs` | `{config_name:str}`，服务端允许的 configs 文件基名 | `202 RunView`；配置不合法 422，已有活动运行 409；启动失败通过 RunView/日志反馈 |
| `POST /runs/{run_id}/stop` | `{}` | `202 RunView`；重复 stop 返回当前状态；新启动需新 run_id |
| `GET /runs/{run_id}` | 无 | `200 RunView`；只读 |
| `GET /runs/{run_id}/sessions/{session_id}/state` | 无 | `200 SessionView`，session_id 必须属于该 run；仅该座位 self_hand，其他座位只公开剩余张数 |
| `GET /runs/{run_id}/sessions/{session_id}/decisions` | `after_seq=0,limit=50` | `200 DecisionPage`，按 request_opened 的 seq 分页；不含其他座位私牌 |
| `GET /runs/{run_id}/sessions/{session_id}/decisions/{request_id}` | 无 | `200 DecisionDetail={state,candidates?,candidate_actions,proposal?,review?,execution?,calls,log_complete}`；各字段沿用本文件结构，未知为 null |
| `GET /runs/{run_id}/reports` | 无 | `200 {items:[{report_id,kind,status,created_at}]}`；报告摘要，无在线模型调用 |
| `GET /runs/{run_id}/reports/{report_id}` | 无 | `200 ReviewReport或EvaluationReport`；对局记录关闭后允许读取，在线运行时 409 |

`DecisionSummary={request_id:str,opened_seq:int,round_id:int,stage:Stage,source:str?,execution_status:str?,updated_at:str,log_complete:bool}`；`DecisionPage` 与 EventPage 使用相同游标/完整性字段，但 items 为 DecisionSummary[]，next_after_seq 取最后一个 opened_seq。

B08 的 `candidate_actions:LegalAction[]` 只投影已登记候选对应的牌型/牌张，来源为同请求严格校验的 RequestContext.legal；不是原始平台对象，也不返回无关座位。查询缺少上下文/候选归属错误时返回410，不补造局势。服务端启动显式装载旧档案，后续 GET 只访问缓存；当前初值最多8份启动归档、每份20000条，活动运行沿用 logs.cache_events。

`SessionView={run_id,match_id,round_id,session_id,seat,state_version,view_version:int,updated_at:str,status:str,state:TableView?,active_request_id:str?,decision_stage:str?,latest_execution:ExecutionRecord?,log_complete:bool,error:ErrorInfo?}`；首次 beginning 前 round_id=0、state 可空，建立请求后 binding.round_id 仍从 1 起。view_version 随展示变化递增，不能当作决策有效性版本。`TableView={stage:waiting或play或tribute或back或settled,self_hand:Card[],level_rank:str?,team_ranks:(str?)[],remaining_counts:(int?)[],leader_seat:Seat?,leading_action:WireAction?,finished_order:Seat[],facts_status:trusted或degraded}` 是不绑定 request 的当前牌桌投影，使尚未轮到本人时也能展示本人手牌；它不能反过来充当决策快照。客户端每秒刷新当前 RunView 摘要与所选 state，只接纳同身份更大的 view_version；摘要同步本地运行列表，完成后恢复控制。跨场自动跟随原座位，座位分批加入时继续等待；用户手选旧场则暂停自动跟随。历史详情按需读，不轮询整场明细。模型文本作为文本显示，不能当 HTML 执行。

页面增加“已生成复盘”入口：使用已有 `GET /runs/{run_id}/reports` 展示报告列表与状态，打开 report_id 后展示内容，区分当时事实、事后结果、解释和建议。模型文本按文本渲染；空列表显示尚无报告，partial/failed 明示不完整/失败。报告条目的 session_id 由程序从已关闭的对局记录派生，页面以报告 run_id、条目 session_id/request_id 打开已有决策详情接口，并显示对应 evidence_event_ids；缺失、跨请求或不可查询的证据明确标注，不能猜造链接。报告页与原决策页的 GET 均不生成报告、重调模型或出牌，跳转不改变在线策略观察座位。

错误统一为 `{error:ErrorInfo}`：403 非允许 Host/Origin，404 未找到，409 运行状态冲突，410 历史不可用，422 参数错误，503 应用不可用。410 在已知时另返回顶层 `retained_from_seq`，页面以其减1作为恢复游标；缺失锚点的残留请求可以明确跳过，不反复请求游标0。不存在 HTTP“替模型选牌”或“重试旧动作”接口；点击理由和历史不触发新决策。控制启动返回 run_id 后可保存到页面本地，刷新后查询同一运行。

### 12.4 复盘与统计契约

`RunSummary={schema_version,run_id,config_id,closed:bool,log_complete:bool,last_persisted_seq:int,pending_call_ids:str[],unconfirmed_submission_ids:str[],error:ErrorInfo?}`。运行开始保存脱敏 config.json，过程中追加 events.jsonl，结束时在有限等待内排空记录器并生成 summary.json。汇总可以附带从事件算出的统计，不另立胜负权威。

B02 采用一个有界队列和单写入线程。先写 `summary.pending`，该文件同时是未确认关闭标记；writer 完成事件/汇总发布后，关闭等待方在未超时的前提下执行短的本地元数据提交，移除 pending 并返回 `closed=true`。关闭超时则停止准入与后续写入，返回 `closed=false/log_complete=false` 并保留 pending；已经开始的单次文件 I/O 可能晚结束，包括迟到出现 `summary.json`，但不能恢复内存关闭结果。读取器只要发现 pending 就判为未可信闭合，即使 summary.json 声称 closed=true 也不采信；不得自动清理标记以把失败改成成功。未可信闭合的目录可以读取诊断，不能作为已关闭源进入复盘。不增加写入进程管理或关闭后修订链。

首版只关闭一次对局记录；关闭时未确认动作与未知用量保持未知，不继续等待远端回复。取消后仍未结束的工作不能再写已关闭日志或启动新副作用。取消失败不等于未计费。报告引用 run_id、config_id 和原始 event_id，源记录保留；不建设父 manifest、补充文件 hash 链或关闭后自动修订。崩溃/写失败保留不完整标记，缺证据不认定通过。离线复盘自己的调用用量写在报告/任务记录中，不回写已关闭的对局事件。


以下段落描述保留的 B09/v1 路径；当前 v2 差异见后文。B09复盘通过统一运行入口的离线命令启动；默认选择同一座位最多3个关键请求，也可明确request_id只检查一条。`ReviewReport={report_id,run_id,config_id,status:completed或partial或failed,items:[{request_id,session_id,evidence_event_ids,at_time_facts,later_facts,assessment,suggestion}],usage,errors}`；at_time_facts 与 later_facts 分开，候选和动作必须引用真实记录。模型仅生成条目内容及所引用的 request_id/event_id；report_id、run_id、config_id 和条目 session_id 由程序根据已关闭的对局记录校验后补齐，不接受模型猜测归属。每条决策引用必须属于本报告源 run/session/request，later_facts 引用可以来自该源 run 的后续公开事件，须标明事后身份；缺失/越界引用标依据不足且不生成错误跳转。无对照模拟不输出“换某牌必胜”。在线新批次启动时管理器停止未完成复盘，报告标 partial；已发调用成本继续按已知证据记录。

B08 先落实报告读取 DTO：ReviewReport 另含 `schema_version="1.0",kind="review",created_at`；item 的当时/事后事实为字符串数组，判断与建议为字符串。item 增加只读 `evidence_available/evidence_error`，读取层根据源记录重新计算，不能相信文件或模型声明；错误引用禁用跳转，并把 completed 报告降为 partial。`ReportPage={items:ReportSummary[],log_complete,errors}`，损坏/超限文件只给安全错误。ReportStore 启动或程序显式注册时一次加载（每源最多100份，每文件512KiB），GET 不读盘、不调用模型。B09 已通过 register/启动装载交接新报告，并实现独立离线权限。ReviewReport增加coverage（selected_requests范围、可用/选定/已复盘请求、日志完整性）与generation（离线配置ID、提示版本、模型、输入字节），均由程序填写。completed只表示本次选定范围成功解析并通过引用门槛，绝不是“所有文字事实正确”；真实样本的事实错误见实施计划7.11。旧报告页面继续标注模型归纳与原始记录。

当前默认 `b09-offline-v2` 只接受模型输出 request_id、evidence_event_ids、assessment、suggestion，拒绝模型填写事实或核验标记。程序从校验后的请求/执行/公开事件生成 at_time_facts/later_facts，并补齐事实需要的引用。执行结果置于事后栏；贡还后未知手牌与张数不补全。ReviewReportItem 新增 `facts_source: model|program = model`、`facts_verified: bool = false`；读取层仅在v2声明、源记录完整、重新生成的文字与必要引用均一致时标核验成功。伪造/不一致声明保留原文、标partial并附PROGRAM_FACTS_UNVERIFIED。模型分析建议不在事实核验范围。旧v1显式配置保留原路径和原输出；新事实回放及真实效果边界见[修复记录](事实语义修复记录.md)。

`EvaluationReport` 至少包括 `run_ids,config_ids,unit:round或match,cohort,counts,performance,latency,model_usage,quality`。cohort 包含队友/对手、座位、平台/规则/预算、model/prompt/candidate/fallback 版本、数据 split、`deal_group_id?` 和 `paired_verified:bool`；只有实际牌局对应验证通过才能为 true。

- `counts`：启动数、可信已结算数、已判胜/负/平数、未结算中断数、仍待结果数；另列 `log_incomplete_count`，它与结算结果可以重叠，不能强行相加成启动总数。按唯一 match_id/round_id 去重四个座位看到的同一结算；以指定评测队伍为单位，不把四座位当四场样本。多份结算冲突不择一取胜，标待核对。
- `performance`：胜率为 win/(win+loss+draw)，分子/分母都输出，分母零为 null。平台明确判负计 loss 并另列原因；无结算不能补判。小局先报告 finish_order/team_finish_order 和平台给出的级别变化；尚无经过定义的数值小局得分时不自造平均分。
- `latency`：从请求接收到首次 write_started 的延迟，以及完整决策/模型/工具耗时，单位 ms；p50/p95/max 同时报告有效样本数。没有写出的样本另列，不用 0 混入；超时/中断有单独计数。小样本分位数不等于正式性能保证。
- `model_usage`：slots_used、calls_started、transport_requests、输入/输出/总 Token 的已知合计，以及各项缺失调用数；有缺失时总费用/总 Token 为 null，并单独给 known_subtotal。线上与离线分开，0 模型调用的 V0 可记已知零。
- `quality`：按 Session 最终采纳决定去重的规则兜底率（已有 submission 以 ExecutionRecord.source 为准，迟到 proposal 不计）、主调用无效率、战术复核启动/成功/改选率、repair 次数、未确认提交数、超额请求和非法提交数。每项输出 numerator/denominator：兜底分母为非唯一、请求可信且已启动本地决策处理的请求，包含工具准备阶段；分子为其中被 Session 采纳 fallback 的请求，未采纳动作便作废者单列，保证分子是分母子集；主无效分母为已完成并收到内容的主调用；复核改选分母为成功战术复核；repair 不混入复核改选。截止采用已登记 main 仍归 main；未成功 begin_call 的战术复核不计复核启动，只有 role=review 且 begin_call 成功才计入。兜底始终按最终 source=fallback 统计；保留 main 的 skipped 不计兜底，repair 未开始而转规则备选的 skipped 仍计兜底。另列模型超时、提交截止未发出与记录缺口。

B09的 `evaluate(records,report_id,created_at,unit)` 只读载入记录，在固定ID/时间与输入下结果确定；cohort保留源配置/评价队伍、混合条件标记，paired_verified固定false。输出分母、已知小计与缺失数；线上统计不读取离线报告用量，离线用量保存在各报告/独立execution文件中。当前官方协议无平局信号，未知胜方不得推成draw；归一win/loss/draw函数单独测试平局分母。round只报告名次/级牌，不发明分数。

统计输出必须列出完整性边界：已结算但日志缺失的比赛可以用于有可信证据的成绩统计，不能用于缺失回合的精确延迟/调用统计；没有足够结算证据则胜负未知。预算耗尽后退化规则的 V1/V2 保留原配置标签并报告降级数量，不冒充完整 LLM 策略样本。
