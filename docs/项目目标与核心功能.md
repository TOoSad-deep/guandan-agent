# 基于 LangGraph 与大语言模型的掼蛋决策 Agent

> 公开版本说明：本文中标为“原工作区”的材料未随仓库提供；可公开核对的内容见[证据说明](evidence/README.md)。

## 1. 项目定位

本项目是面向学校课程设计的掼蛋 AI 系统。基于课程提供的 OpenGuanDan 比赛平台，调用现有大语言模型，结合规则工具、对局状态管理和 LangGraph 流程编排，实现能够自主参赛、解释决策、记录过程和分析结果的掼蛋 Agent。

项目采用“主决策 Agent + 条件触发的战术复核 + 赛后复盘”的方案，不进行模型训练或微调。实现规模以三人课程项目为参考，重点完成可运行、可展示、可评测的系统。

本文约定项目目标、第一版功能范围及团队自验标准，作为后续开发和答辩材料的基础。文中功能均为计划建设内容，不表示已经实现；课程正式验收要求以教师发布的说明为准。

## 2. 整体目标

### 2.1 自主完成对局

Agent 能够连接比赛平台，接收当前局势和合法动作，完成出牌、过牌、进贡、还贡等操作，并读取单局及整场结算结果。模型调用异常时，系统能够在平台时限内使用合法备选动作。

### 2.2 结合规则与模型进行决策

程序负责准确记牌、手牌特征计算、候选动作筛选和合法性校验；大语言模型根据这些信息，权衡自己走牌、队友配合和对手威胁，在合法候选中选择动作。

### 2.3 对关键决策进行有限复核

使用明确的触发条件识别关键局面，由战术复核 Agent 检查主 Agent 的选择。普通局面保持简洁流程，关键局面允许增加一次复核，并统一限制模型调用次数和总耗时。

### 2.4 展示决策并支持复盘

通过对局界面、决策面板和回合日志，展示选中动作、简短理由、复核结果和执行状态。对局结束后生成有日志依据的关键回合分析。

### 2.5 通过实验评价系统

设置规则基线和不同 Agent 配置，在明确的对战条件下比较团队成绩、响应时间、调用成本及稳定性，分析规则工具和战术复核的实际作用。

## 3. 第一版范围

| 类别 | 范围 |
| --- | --- |
| 必做功能 | 平台接入、状态与记牌、简单手牌评估、候选筛选、主 Agent 决策、条件复核、校验与兜底、基础界面、日志、赛后复盘、实验统计 |
| 可选扩展 | 更丰富的回放界面、多个模型的横向对比、复核触发条件调优、更细的手牌评分特征 |
| 暂不纳入 | 模型训练与微调、复杂残局树搜索、在线自动修改策略、无限轮多 Agent 辩论、向量数据库、完整多人社交游戏平台 |

第一版保留两个在线 LLM 角色：主决策与战术复核。两个角色可以使用同一个模型，通过不同提示词和输出结构区分职责。赛后复盘作为独立的离线任务，不占用比赛中的决策时间。

手牌分析先采用可解释的启发式指标，不要求实现全局最优组牌。演示界面优先复用可用的平台牌桌，并补充决策面板；具体集成方式在平台运行验证后确定。

## 4. 核心功能

### F01 比赛平台接入

- 连接指定版本的 OpenGuanDan 平台，接收动作请求和状态通知。
- 按平台协议完成创建或加入房间、出牌、进贡和还贡。
- 从平台当前提供的合法动作中选择并提交完整动作。
- 读取平台结算结果，区分小局结束和整场结束。
- 将平台通信与 Agent 决策分开，便于独立调试和替换策略。

**功能结果：** 规则基线和 LLM Agent 均可通过同一接入模块完成对局。

### F02 对局状态与记牌

维护本人当前手牌、当前级牌、座位与队友关系、各家剩余张数、公开出牌历史、当前领先动作及出牌者，以及对局阶段。

状态分为三类：

| 状态类别 | 示例 | 更新依据 |
| --- | --- | --- |
| 已确认事实 | 本人手牌、对手剩余两张、队友上一轮出了对子 | 平台消息和确定性程序逻辑 |
| 模型判断 | 对手可能持有对子、当前应优先协助队友 | 模型分析，保留不确定性 |
| 执行状态 | 当前决策编号、已选动作、提交状态、调用次数 | 本地执行过程与平台反馈 |

重复牌按数量记录；进贡和还贡发生后同步更新已知牌信息。公开历史与当前状态分别保存，避免仅依赖不断增长的聊天记录。

**功能结果：** 每次决策获得一致的局势快照，模型判断不会覆盖平台事实。

### F03 手牌分析与候选筛选

对本人手牌和合法候选动作计算简单特征，包括：

- 出牌数量、剩余张数和剩余组合数量估计。
- 散牌、对子、顺子、炸弹等结构。
- 拆散已有组合、消耗控制牌或配牌的代价。
- 队友当前是否领先、对手是否临近走完等局势特征。

候选较多时，用规则评分筛选适量动作供模型选择，保留合法过牌、直接走完和关键拦截等必要选项。候选数量作为可调参数，不在第一版固定为理论最优值。

分析剩余手牌结构时，应考虑其可形成的组合，不能仅使用当前跟牌列表代替全部组牌可能。剩余组合数量只是评估特征，不等于实际走完所需回合数。

**功能结果：** 为模型提供带有结构化特征的候选列表，并为异常兜底提供规则排序。

### F04 主决策 Agent

输入当前可见局势、公开历史摘要、手牌分析和候选动作。根据局势权衡自身走牌、帮助队友、保留控制牌及阻止对手走完，返回结构化结果：

- 所选候选动作编号。
- 简短、可展示的选择理由。
- 需要注意的局势风险。

模型不得自行编造出牌组合。决策理由用于解释选择，不作为动作合法或策略最优的证明。

**功能结果：** 将候选动作转换为一个待校验的决策结果。

### F05 条件触发的战术复核

由程序根据局势、候选动作及主 Agent 输出决定是否触发复核。初版触发条件包括：

- 对手仅剩一两张牌，需要判断是否必须拦截。
- 准备使用炸弹或明显破坏剩余手牌结构。
- 准备压过当前领先的队友。
- 主决策输出格式异常或动作编号无效，且仍有调用和时间预算。

复核 Agent 使用同一份局势及候选快照，检查原动作，可以维持原选择，也可以直接返回另一个候选动作。复核最多一次，不再发起新一轮复核。

触发条件表示“值得检查”，不表示原动作一定错误。复核是否改善表现通过对照实验评价。

**功能结果：** 输出最终建议动作，并记录是否修改主决策及修改理由。

### F06 动作校验与异常兜底

提交前由程序检查输出结构、动作编号、完整动作合法性，以及动作是否仍对应当前有效请求。每次决策绑定决策编号、局势版本和候选快照，防止迟到响应用于新的局势。

在线模型调用规则：

- 普通局面最多一次调用，触发复核时最多两次调用。
- 只有一个合法动作时，可以直接执行。
- 所有在线模型调用及重试共享同一总预算，不允许底层自动重试突破上限。
- 超时、调用失败或最终校验失败时，使用当前有效请求下的规则备选动作。

发送动作后，根据平台反馈记录执行结果；网络发送成功不等于平台已经接受。提交状态不明时不盲目重复发送，先按协议核对状态。

**功能结果：** 在有效请求和可用连接下返回合法动作，并准确区分待提交、已发送、已确认与失败状态。

### F07 基础界面与决策记录

展示当前牌局及必要的 Agent 信息：所选动作、简短理由、复核是否触发、是否改变动作、耗时和执行结果。

保存按回合组织的日志，支持查看每次决策的输入摘要、候选动作、输出、复核结果、兜底原因及平台反馈。模型调用和比赛通信不阻塞界面交互。

基础回合日志浏览属于必做功能；完整的动画回放与复杂图表属于可选扩展。

**功能结果：** 能在答辩中展示一次正常决策、一次关键复核和一次异常兜底过程。

### F08 赛后复盘

对局结束后，从日志中选取关键回合，交给模型生成复盘内容：当时的可选动作、实际选择、复核意见、后续结果，以及值得继续验证的策略问题。

每条复盘意见关联具体回合。可用当时可见信息评估决策，也可单独描述实际后续结果；不得把事后才知道的信息当作当时应该知道的事实。没有额外模拟或对照证据时，不声称另一个动作必然获胜。

复盘建议由开发者检查，用于下一版本设计，不自动改写在线提示词或策略。

**功能结果：** 生成可回查日志的关键回合分析和待验证改进项。

### F09 对战评测与统计

保留三个可切换版本：

| 版本 | 配置 | 比较目的 |
| --- | --- | --- |
| V0 规则基线 | 使用确定性的规则策略 | 提供稳定对照和兜底策略 |
| V1 工具辅助 LLM | 手牌工具与候选筛选，加一次 LLM 决策 | 观察在规则工具基础上引入模型的表现 |
| V2 条件复核 Agent | 在 V1 基础上启用关键局面复核 | 评估复核的收益与额外成本 |

V1 与 V2 使用相同的候选生成规则、模型配置和兜底策略，便于判断复核的影响。该三版本设计不单独证明每一项工具的作用；需要时再增加关闭某个工具的消融实验。

记录团队成绩、按平台口径定义的胜率、有效对局数量、响应耗时、模型调用次数、Token 用量、可核算费用、超时与兜底次数，以及复核修改动作的比例。小局成绩和整场升级赛胜负分开统计，失败对局单独报告，不悄悄剔除。

尽量统一对手、队友配置、规则版本和时限。平台支持时，使用相同发牌并轮换座位；同一发牌的轮换结果不能当作互相独立的样本。不能控制发牌时，明确记录这一限制。

**功能结果：** 输出可追溯到对局日志的统计结果，并解释收益、成本和仍存在的问题。

## 5. LangGraph 流程设计

主流程：

> 接收局势 → 更新状态 → 工具分析与候选筛选 → 主 Agent 决策 → 判断是否复核 → 最终校验 → 提交动作 → 记录平台反馈。

| 分支 | 处理方式 |
| --- | --- |
| 唯一合法动作 | 直接进入校验和执行 |
| 普通局面 | 主 Agent 决策后进入最终校验 |
| 关键局面或可修复的输出异常 | 在预算允许时进入一次战术复核 |
| 模型失败、超时或最终校验失败 | 使用规则备选动作 |
| 请求过期 | 放弃旧决策，根据平台新状态重新处理 |
| 对局结束 | 保存结算信息，启动独立的赛后复盘 |

LangGraph 主要承担状态传递、条件路由、节点结果记录和受限执行。规则计算节点由普通 Python 函数实现，只有需要局势权衡的节点调用模型。

状态快照可用于调试和本地流程恢复。Checkpoint 不等于比赛服务器的恢复机制；断线后必须核对平台状态。若平台不支持恢复原对局，应记录中断，不能直接重放旧动作。

## 6. 模块划分与建议分工

| 模块 | 主要内容 | 建议负责人 |
| --- | --- | --- |
| 平台与状态模块 | 通信、协议适配、状态更新、记牌、动作提交与确认 | 成员 A |
| 策略与 Agent 模块 | 手牌特征、候选筛选、规则基线、LangGraph、提示词和复核逻辑 | 成员 B |
| 展示与评测模块 | 决策面板、回合日志、赛后复盘、对战统计与实验报告 | 成员 C |

三人先共同确定可见局势、候选动作和决策结果的数据结构，再分别开发。成员 B 的工作量较集中，候选特征或复核规则可由其他成员协助完成。

核心边界为：平台模块提供可见局势和合法动作；策略模块返回候选编号及说明；执行模块校验并提交；展示和评测模块消费过程日志与已确认结果。

## 7. 团队自验标准

以下为项目内部完成标准，不代替课程正式评分要求。

- [ ] 在指定平台版本上完成连续对局，覆盖出牌、过牌、进贡、还贡与结算流程。
- [ ] 在线决策仅使用本人手牌和平台允许获取的公开信息。
- [ ] 记牌中的重复牌、贡还牌和剩余张数更新一致。
- [ ] 主 Agent 与复核 Agent 均输出可校验的候选动作编号。
- [ ] 普通、关键和异常三种决策路径均可演示。
- [ ] 人为制造超时、错误编号和解析失败时，能按预算进入合法兜底。
- [ ] 过期响应不会被提交到新局势，日志不会把未确认动作标记为已执行。
- [ ] 可按回合查看决策理由、复核修改和平台反馈。
- [ ] 赛后复盘能定位到具体回合，区分事实、推测和待验证建议。
- [ ] 完成 V0、V1、V2 的对比实验，报告条件、样本数量、成绩和成本。
- [ ] 提交源代码、运行说明、实验结果、答辩 PPT 和按个人分工撰写的报告。

项目不预设尚未验证的胜率目标。若复核或模型决策未带来提升，应据实报告，并分析触发条件、上下文、延迟或策略设计方面的原因。

## 8. 实施顺序

1. **平台与规则基线：** 跑通通信、状态维护、规则策略、提交和结算，确认能够完成对局。
2. **主 Agent：** 加入手牌分析、候选筛选和结构化模型输出，完成 V1。
3. **LangGraph 与复核：** 固化状态和分支，增加条件复核、调用预算、最终校验与兜底，完成 V2。
4. **展示与复盘：** 完成基础界面、回合日志和有证据关联的赛后分析。
5. **评测与交付：** 冻结测试版本，运行对照实验，整理结果、说明文档和答辩材料。

## 9. 实施前需核实的条件

| 条件 | 对方案的影响 |
| --- | --- |
| 比赛是否允许外部模型 API | 决定是否能使用远程 LLM 作为在线决策器 |
| 教师提供的平台版本与示例 | 决定通信协议、动作格式、结算和连接恢复方式 |
| 单步响应时限 | 决定模型选择、复核预算和兜底触发时间 |
| 模型供应商、模型名称和调用预算 | 决定接入配置、结构化输出方案、实验规模和成本统计 |
| 平台界面与人工演示要求 | 决定牌桌复用和决策面板的集成方式 |
| 是否支持固定发牌或保存初始局面 | 决定是否能做严格的配对对比实验 |

这些条件应在平台接入阶段确认，避免后期调整核心接口。
