# 掼蛋 Agent 项目开发流程与阶段产出

## 1. 文档目的

本文将项目从目标梳理到开发交付的步骤整理为可执行的流程，说明每个阶段需要解决的问题、应形成的产出，以及进入下一阶段前需要具备的条件。

项目范围以 [项目目标与核心功能](项目目标与核心功能.md) 为依据：面向学校课程设计，使用现有大语言模型、规则工具和 LangGraph，实现主决策、条件复核、异常兜底、对局展示及赛后复盘，不进行模型训练。

本文是后续工作的流程说明，不表示各阶段已经完成，也不替代教师的正式课程要求。

## 2. 总体顺序

> 项目目标与范围 → 需求 Spec 初稿 → 关键技术验证 → 架构与技术选型 → 接口细化与项目结构 → 实施计划 → 开发、验证与交付。

推进时遵循三个原则：

1. **先明确行为，再选择实现方式。** 先说明系统要做什么、什么情况算成功，再判断需要哪些模块和技术。
2. **先验证关键条件，再固定架构。** 平台协议、模型响应时间和比赛限制可能改变方案，应尽早通过小实验确认。
3. **先确定模块职责，再组织代码目录。** 目录应反映模块边界，文件名和内部拆分可以在实现过程中调整。

需求和架构允许相互迭代。验证发现问题时，更新相关约束和设计，再调整实施计划。无需等所有文档完全定稿才开始小规模技术验证。

## 3. 阶段一：项目目标与范围

### 需要回答的问题

- 项目解决什么问题，最终要展示什么？
- 第一版必须包含哪些功能，哪些可以后续增加？
- 项目规模、人员和课程周期是否支持这些功能？
- 哪些属于课程要求，哪些属于团队自行选择的实现方案？

### 阶段产出

已有的 [项目目标与核心功能](项目目标与核心功能.md)，用于约定功能范围、系统定位和团队自验标准。

### 进入下一阶段的条件

团队对第一版范围有一致理解，能够说明哪些功能优先完成，以及哪些功能暂不投入开发。

## 4. 阶段二：需求规格初稿

需求 Spec 描述系统应该表现出什么行为，暂不要求确定每个类、函数或框架接口。

### 需要细化的内容

为每项核心功能补充：

| 项目 | 内容 |
| --- | --- |
| 触发场景 | 什么事件发生后需要执行该功能 |
| 输入 | 功能能获取哪些数据，哪些数据不可使用 |
| 预期行为 | 系统应完成什么处理 |
| 输出与结果 | 应产生什么结果，如何确认结果有效 |
| 异常情况 | 输入缺失、调用失败、超时、请求过期等如何处理 |
| 验收条件 | 用什么具体案例判断功能完成 |

例如，动作选择功能可以写为：

> 模型返回不属于本次候选集合的动作编号时，系统不得直接提交。在当前请求仍有效、且仍有时间和调用预算时，可以进入一次修复或复核；否则选择当前请求下的合法规则备选动作，并记录原因。请求已过期时，放弃旧决策。

这段描述规定了行为，但没有预先决定用哪个类、哪种消息格式或哪个 LangGraph 节点实现。

### 阶段产出

[需求与接口规格.md](需求与接口规格.md) 的需求部分，包括正常路径、异常路径、约束和可观察的验收条件。阶段二形成了 v0.1 需求初稿，当前已在阶段五及后续实现修订为 v1.10 接口基线；原需求与验收案例保留。

### 进入下一阶段的条件

核心功能的输入、输出和成功条件清楚；仍不确定的事项已列出，并能转化为待核实问题或小实验。

## 5. 阶段三：关键技术验证

用最小实验确认会影响架构的条件。此阶段允许编写少量验证代码，但实验脚本不自动成为最终工程结构。

| 验证项 | 最小验证方式 | 需要获得的结论 |
| --- | --- | --- |
| 平台接入 | 连接指定平台，读取真实消息，提交一个合法动作 | 协议、消息结构与动作提交方式是否明确 |
| 对局流程 | 使用简单规则策略完成一局，并检查阶段切换 | 状态更新、过牌、结算等是否能正确衔接；贡还牌需要另覆盖对应场景 |
| 模型输出 | 输入固定局势和候选列表，检查结构化输出 | 动作编号是否可解析、能否校验，失败有哪些类型 |
| 响应时间 | 记录代表性请求的耗时和调用用量 | 单次决策及额外复核能否满足预算 |
| 比赛限制 | 核对教师说明或平台规则 | 是否允许外部 API，单步时限如何规定 |
| 展示方式 | 检查平台界面和可用日志 | 能否复用牌桌，决策面板如何接入 |

实验记录包含环境或版本、操作步骤、输入、观察结果，以及仍未覆盖的情况。一次成功请求不能证明长期稳定，也不能证明策略强度。

### 阶段产出

在 [架构与技术选型](架构与技术选型.md) 中记录验证结论；保留必要的验证脚本和日志。可以明确标记为“已验证”“不支持”或“待验证”。当前已有本地平台、离线模型流程和固定局势下真实 DeepSeek 调用的验证记录，课程外部约束仍待确认。

### 进入下一阶段的条件

关键依赖有可行路线，能够据此确定主要架构。尚未解决的问题应有影响说明和临时方案，例如复核耗时过高时先关闭在线复核。

## 6. 阶段四：架构与技术选型

根据需求和验证结果确定系统如何组成，以及为什么这样选择。

### 需要确定的内容

- **模块职责：** 平台通信、状态管理、手牌工具、Agent 决策、动作执行、界面、日志和评测各自负责什么。
- **数据流向：** 平台消息如何变成决策输入，决策结果如何经过校验并提交，日志如何被界面和评测读取。
- **状态归属：** 哪个模块维护当前局势，哪些字段来自平台，哪些字段只是模型判断。
- **LangGraph 流程：** 哪些节点执行 Python 逻辑，哪些调用模型，何时复核、兜底或结束。
- **异常与时间预算：** 模型超时、输出异常、过期响应和连接中断分别由谁处理。
- **技术选择：** Python、LangGraph、模型接口、界面形式、日志或状态存储方式，以及必要依赖。

对关键选型记录“满足什么需求、有哪些限制、为什么适合当前规模”即可。模型供应商、数据库和界面框架等尚未确认的部分，不应提前包装为已经确定的依赖。

### 阶段产出

[架构与技术选型.md](架构与技术选型.md)：模块职责、主流程与分支、状态管理方式、技术选择依据和已知限制。阶段四已形成架构基线，当前 v1.7 包含阶段五目录、图示、接口映射及 review 修订，并在附录 A 保留阶段三实验记录；设计完成不表示全部模块已经实现。

### 进入下一阶段的条件

能够沿着一次真实决策说明各模块如何协作，并明确每个模块的输入、输出、状态修改权限和异常责任。

## 7. 阶段五：接口细化与项目结构

在架构基础上补充技术 Spec，并让代码目录反映已经确定的模块边界。

### 技术 Spec 的重点

- 可见局势、候选动作、决策结果、复核结果和执行结果的数据结构。
- 决策编号、局势版本和候选快照之间的关系。
- 平台消息与内部数据结构的转换规则。
- 各模块的调用接口、返回值及错误处理约定。
- 模型输出格式、校验条件、调用次数和耗时预算。
- 日志字段、配置项和对战统计口径。

例如，上述非法动作需求可以进一步细化为：

> 决策结果包含 `action_id`。校验模块检查该编号是否属于绑定的候选快照，并检查请求是否仍有效。校验结果决定进入执行、有限复核、规则兜底或放弃过期决策的分支。

这里的字段名属于设计示例，正式命名应在接口文档中统一。

### 项目结构的重点

确定源码、配置示例、测试、演示工具和实验输出分别放在哪里；划清平台适配、策略逻辑和展示代码的边界。先稳定主要目录与公共接口，内部文件可随着实现调整。

### 阶段产出

- 已补全 [需求与接口规格](需求与接口规格.md) 第 8—13 节：数据、协议映射、模块调用、两层截止、模型预算、HTTP、日志、配置与统计。
- 已在 [架构与技术选型](架构与技术选型.md) 第 13 节确定目录、依赖方向、三人协作面及探针迁移范围。
- 已提供 [合成契约样例](examples/phase5-contract-example.json) 与 T01—T13 联调案例；样例用于开发对照。后续 B01 已对其中 context 子结构进行类型测试并建立基础工程，其余业务案例仍待对应批次。

### 进入下一阶段的条件

成员可以依据接口独立开发或使用模拟数据联调，且不会出现多个模块重复维护同一份权威状态的情况。

## 8. 阶段六：撰写实施计划

把需求和设计拆成有依赖关系、可验证的任务。优先安排能形成完整运行路径的阶段成果。

### 推荐的阶段划分

| 里程碑 | 主要工作 | 可展示结果 |
| --- | --- | --- |
| M1 规则对局 | 平台接入、状态更新、规则策略、提交和结算 | 不调用模型也能完成对局 |
| M2 主 Agent | 手牌分析、候选筛选、模型接口、LangGraph 基础流程和校验兜底 | 完成工具辅助的 LLM 对局 |
| M3 条件复核 | 风险触发、复核节点、调用预算和异常路径 | 可展示普通、复核和兜底三种流程 |
| M4 展示与复盘 | 基础面板、回合日志浏览、赛后分析 | 能检查具体回合并解释决策 |
| M5 评测与交付 | 冻结测试配置、运行对比实验、整理说明和答辩材料 | 形成可追溯的实验结果和交付包 |

基础日志应从 M1 开始记录，M4 再完善浏览和复盘能力。上述里程碑是计划划分，不表示其他阶段此前不能并行准备。

### 每个任务至少写清

任务内容、依赖、负责人、产出和验收方法。例如：

| 项目 | 示例 |
| --- | --- |
| 任务 | 实现模型动作编号校验 |
| 依赖 | 候选快照和决策结果结构已确定 |
| 产出 | 校验逻辑及明确的失败原因 |
| 验收 | 有效编号、越界编号、空输出和过期请求均进入预期分支 |

### 阶段产出

[实施计划.md](实施计划.md) v1.2 已形成：M1—M5 共 24 项任务，明确依赖、A/B/C 主责、产出及验收，并映射 31 个 AC 和 T01—T13。未提供实际工期时按工作批次安排；工程任务均待执行。

### 进入下一阶段的条件

最先开始的一批任务没有未解决的关键依赖，每项任务都有可以实际检查的完成条件。

## 9. 阶段七：开发、验证与交付

按照实施计划逐阶段开发。每完成一段可运行路径，就检查行为、记录结果并修正文档。

验证分为不同层次：

| 层次 | 要证明的内容 |
| --- | --- |
| 模块验证 | 计数、候选映射、校验、路由等确定性逻辑符合约定 |
| 联调验证 | 平台、状态、模型和执行模块能够交换正确的数据 |
| 实际运行 | 真实模型调用和真实平台对局能够完成，异常能够按设计处理 |
| 展示验证 | 界面可用，关键回合及复核、兜底过程可以查看 |
| 效果评价 | 在记录清楚的对战条件下比较成绩、耗时、成本与稳定性 |

自动化测试通过不等于已接入真实平台；能够打完一局也不等于策略更强。报告中应分别陈述这些结果。

最终对比保留规则基线、工具辅助单次 LLM、条件复核三个版本。实验后整理源代码、配置示例、启动说明、对局日志、统计结果、复盘示例及课程要求的答辩材料。
